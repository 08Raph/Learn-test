#LESSON What a computer actually does | 12
A computer is a machine that follows instructions. That is all. It does not understand, guess or get tired. It takes **input**, follows a list of instructions called a **program**, and produces **output**.

Think of a kitchen. The recipe is the program. The cook who follows it one step at a time is the **processor** (CPU). The counter where ingredients sit while cooking is **memory** (RAM): quick to reach, but cleared when you finish. The cupboard where food is kept for weeks is **storage** (a disk): slower to reach, but it keeps things when the power is off.

```diagram
 keyboard, mouse,          +-----------+          screen, speaker,
 touch, network   ----->   |    CPU    |  ----->  printer, network
     (input)               +-----------+              (output)
                             ^       |
                             |       v
                       +----------------+      +-----------+
                       |  memory (RAM)  | <--> |  storage  |
                       +----------------+      +-----------+
```

The CPU repeats one tiny cycle billions of times a second: **fetch** the next instruction from memory, **decode** what it means, **execute** it. Each instruction is very small, such as "add these two numbers" or "copy this value there". Everything you see a computer do, from video to games, is built from enormous numbers of these small steps.

> Key idea: A computer is fast and exact, not clever. If the instructions are wrong, it does the wrong thing perfectly.

### Hardware and software
**Hardware** is the part you can touch: the CPU, memory, disk, screen. **Software** is the instructions: the programs. The same hardware becomes a calculator, a piano or a map depending on which software runs.

> In industry: Engineers still think in input, processing, output. When a system misbehaves, the first questions are "what went in?", "what came out?" and "what happened in between?".
#Q A recipe is to a cook as a program is to what?
- The screen
* The processor (CPU)
- The keyboard
! The CPU is the part that follows the instructions, one step at a time.
#Q You are typing an essay and the power goes out before you save. Why is the text lost?
- Storage is erased when the power goes off
* The text was only in memory (RAM), which needs power to hold data
- The CPU deletes unsaved work
! RAM is fast working space that is cleared without power. Saving copies the text to storage, which keeps it.

#LESSON Bits, bytes and binary | 15
Inside a computer everything is stored using tiny switches that are either **off** or **on**. We write off as 0 and on as 1. One such switch is a **bit**. Eight bits make a **byte**.

Why only two values? Because it is easy to build a reliable switch with two states, and very hard to build one with ten.

### Counting in binary
We normally count in **decimal** (base 10): each place is worth ten times the one to its right: ones, tens, hundreds. **Binary** (base 2) works the same way, but each place is worth *two* times the one to its right: ones, twos, fours, eights.

| Place value | 8 | 4 | 2 | 1 |
|---|---|---|---|---|
| Binary digits | 1 | 0 | 1 | 1 |

So binary `1011` means 8 + 0 + 2 + 1 = **11**.

To turn a decimal number into binary, keep dividing by 2 and write down the remainders. Read them from last to first:

```text
13 / 2 = 6 remainder 1
 6 / 2 = 3 remainder 0
 3 / 2 = 1 remainder 1
 1 / 2 = 0 remainder 1      -> read upward: 1101
```

With n bits you can make 2ⁿ different patterns. One byte (8 bits) gives 256 patterns, enough for the numbers 0 to 255.

### Everything is numbers
Text is stored as numbers too: each character has a code (in the common ASCII table, `A` is 65). A picture is a grid of numbers saying how much red, green and blue each dot has. Sound is a long list of numbers measuring air pressure thousands of times a second.

> In industry: Limits you will meet come straight from bit counts. A 32-bit number tops out near 4.29 billion, which is why some old systems ran out of ID numbers or memory addresses.
#Q What decimal number is binary 1010?
- 5
* 10
- 12
! 8 + 0 + 2 + 0 = 10.
#Q How many different values can 4 bits represent?
- 4
- 8
* 16
! Each extra bit doubles the count: 2 × 2 × 2 × 2 = 16.

#LESSON Hexadecimal | 10
Binary is exact but long. `11111111` is hard to read and easy to mistype. Programmers shorten it with **hexadecimal** (hex), which is base 16.

Base 16 needs sixteen digits. We use 0 to 9 and then the letters A to F for ten to fifteen:

| Decimal | 0-9 | 10 | 11 | 12 | 13 | 14 | 15 |
|---|---|---|---|---|---|---|---|
| Hex | 0-9 | A | B | C | D | E | F |

The useful trick: **one hex digit is exactly four bits**. So you can convert by chopping binary into groups of four.

```text
binary   1010 1111
hex         A    F        -> AF
```

To read a hex number, each place is worth sixteen times the one to its right. `2F` is 2 × 16 + 15 = **47**. Two hex digits describe one byte, from `00` (0) to `FF` (255).

Because hex and decimal can look alike, hex is usually marked with `0x` in code (`0x2F`) or `#` in web colours.

### Where you will see it
- **Colours** on web pages: `#FF0000` is full red, no green, no blue.
- **Memory addresses** in error messages: `0x7ffe5c2a`.
- **Raw data** when inspecting files or network traffic.

> In industry: When a program crashes, the report often shows addresses and data in hex. Being able to read it is part of debugging at a low level.
#Q What is hexadecimal F in decimal?
- 10
* 15
- 16
! A is 10, B is 11, and so on up to F, which is 15.
#Q What is hex 1A in decimal?
- 11
* 26
- 110
! 1 × 16 + 10 = 26.

#LESSON Operating systems | 12
If programs talked to hardware directly, every program would need to know how to drive every kind of disk, screen and keyboard, and two programs running at once would fight over them. The **operating system** (OS) solves this. It is the program that runs all the other programs. Windows, macOS, Linux, Android and iOS are operating systems.

The OS does four big jobs:

1. **Runs programs and shares the CPU.** A running program is called a **process**. There are usually far more processes than CPU cores, so the OS lets each run for a few thousandths of a second and then switches. It happens so fast that everything seems to run at once.
2. **Manages memory.** It gives each process its own area of memory and stops one process reading or damaging another's.
3. **Organises storage into files and folders.** A disk is really one enormous row of numbered blocks. The **file system** turns that into named files in folders.
4. **Talks to devices.** Small programs called **drivers** know how to operate each device, so applications do not have to.

```diagram
  +--------------------------------------+
  |  applications (browser, game, editor)|
  +--------------------------------------+
  |          operating system            |   <- programs ask it for things
  +--------------------------------------+
  |  hardware (CPU, memory, disk, screen)|
  +--------------------------------------+
```

A program asks the OS for a service ("open this file", "send this over the network") through a **system call**. The core of the OS that handles these requests is the **kernel**.

> In industry: Almost all servers on the internet run Linux. You will study how operating systems work inside in Stage 3 and again, in depth, in Stage 5.
#Q Why can many programs appear to run at the same time on one CPU core?
- The CPU splits itself into pieces
* The operating system switches between them very quickly
- Each program runs only once per second
! The OS gives each process a short turn and switches so fast that it looks simultaneous.
#Q What does the file system do?
- Speeds up the CPU
- Connects the computer to the internet
* Turns raw storage blocks into named files and folders
! The disk is just numbered blocks; the file system provides names, folders and the record of which blocks belong to which file.

#LESSON What software engineering is | 10
**Programming** is writing instructions for a computer. **Software engineering** is everything needed to build software that many people can rely on for years: understanding what is needed, designing it, writing it, testing it, releasing it, and keeping it working as needs change.

A useful comparison: anyone can build a shed. Building a bridge that thousands of people cross every day needs engineering, because the cost of getting it wrong is high and many people must work together.

### The life of a piece of software
1. **Requirements.** What problem are we solving, and for whom?
2. **Design.** How will the parts fit together?
3. **Implementation.** Writing the code.
4. **Testing.** Checking it does what it should, and nothing it should not.
5. **Deployment.** Putting it where users can reach it.
6. **Maintenance.** Fixing bugs and adding features. This is where most of the time and money goes.

These steps are not done once in order. Modern teams repeat them in small loops, releasing small improvements often and learning from each one.

### What engineers actually do all day
Less typing than you might expect. A lot of reading other people's code, talking with colleagues about what to build, finding out why something is broken, reviewing each other's work, and writing things down so the next person understands.

> Key idea: Code is read far more often than it is written. Writing code that other people can understand is the central skill of the job.

> In industry: Titles vary, but the path is usually junior, mid-level, senior, then staff or principal engineer, or a move into management. This university's six stages follow roughly that growth.
#Q Which activity usually takes the most time and money over a program's life?
- Writing the first version
* Maintenance: fixing and changing it after release
- Choosing a programming language
! Most software lives for years and is changed constantly, so maintenance dominates the cost.
#Q What best separates software engineering from simply programming?
- Engineers use harder languages
- Engineers type faster
* Engineering covers designing, testing, releasing and maintaining software that people rely on
! Programming is one part. Engineering is the whole discipline of building dependable software in teams.

#LESSON Logic: true, false and how to combine them | 12
Programs make decisions, and every decision comes down to a question with two possible answers: **true** or **false**. A value that can only be true or false is called a **boolean**, after George Boole, who worked out the mathematics of logic in the 1800s.

You combine simple true/false statements into bigger ones with three operators.

- **AND** is true only when *both* sides are true. "It is raining AND I am outside" is true only if both are.
- **OR** is true when *at least one* side is true. In logic, OR includes the case where both are true.
- **NOT** flips the value. NOT true is false.

A **truth table** lists every combination:

| A | B | A AND B | A OR B | NOT A |
|---|---|---|---|---|
| false | false | false | false | true |
| false | true | false | true | true |
| true | false | false | true | false |
| true | true | true | true | false |

### Comparisons make booleans
Most booleans come from comparing things: is `age` greater than 17? Is `password` equal to the stored one? Each comparison gives true or false.

A real rule: "You may enter if you have a ticket AND (you are 18 or older OR you are with an adult)." The brackets matter, exactly as in arithmetic.

### A rule worth memorising
**De Morgan's laws** tell you how NOT moves through AND and OR:

- NOT (A AND B) is the same as (NOT A) OR (NOT B)
- NOT (A OR B) is the same as (NOT A) AND (NOT B)

"Not (hungry and tired)" means "not hungry, or not tired".

> In industry: A large share of bugs are logic slips: AND where OR was meant, or a condition that is the wrong way round. Writing out the truth table for a tricky condition is a real professional technique.
#Q When is "A AND B" true?
- When A is true
- When either A or B is true
* Only when both A and B are true
! AND needs both sides to be true.
#Q A is true and B is false. What is "A OR B"?
* true
- false
- It cannot be decided
! OR is true when at least one side is true.

#LESSON Algorithms and pseudocode | 14
An **algorithm** is a list of steps that solves a problem. To be an algorithm the steps must be **clear** (no guessing what a step means), **in order**, and must **finish**.

You already follow algorithms: a recipe, directions to a friend's house, the method you learned for long division.

Before writing real code, engineers often write the steps in **pseudocode**: plain, structured language that is not tied to any programming language. Nobody runs pseudocode; it is for thinking.

Problem: find the largest number in a list.

```text
set largest to the first number in the list
for each remaining number in the list:
    if the number is greater than largest:
        set largest to that number
report largest
```

Notice three building blocks. Every algorithm, however large, is made from just these:

1. **Sequence**: do steps one after another.
2. **Selection**: choose which steps to do (`if`).
3. **Repetition**: do steps again and again (`for each`, `while`).

### Checking an algorithm by hand
Walk through it with a small example, tracking the values. This is called **tracing**. For the list 4, 9, 2:

| Step | Number looked at | largest |
|---|---|---|
| start | 4 | 4 |
| 1 | 9 | 9 |
| 2 | 2 | 9 |

Result: 9. Then try the awkward cases: a list with one number, a list where the largest comes first, a list with equal numbers. Does it still work?

> Key idea: If you cannot explain the steps in plain language, you are not ready to write the code. Confused code comes from confused thinking.
#Q Which of these is NOT required for something to be an algorithm?
- The steps are clear
- It finishes
* It is written in a programming language
! An algorithm is the idea of the steps. It can be written in plain language, pseudocode or a diagram.
#Q What are the three building blocks of every algorithm?
- Input, output, storage
* Sequence, selection, repetition
- Add, subtract, multiply
! Steps in order, choices between steps, and repeated steps.

#LESSON Flowcharts | 10
A **flowchart** is an algorithm drawn as a picture. Some people find the shape of the logic easier to see this way, especially where the path splits.

The standard shapes:

| Shape | Meaning |
|---|---|
| Rounded box | Start or end |
| Rectangle | A step to do |
| Diamond | A yes/no question (a decision) |
| Slanted box | Input or output |
| Arrow | Which step comes next |

Here is "is this number even or odd?" as a flowchart:

```diagram
        ( start )
            |
     / read number /
            |
            v
   < remainder of        yes
     number / 2 is 0? > ------> / say "even" / ---+
            | no                                  |
            v                                     v
     / say "odd" / -----------------------------> ( end )
```

A loop appears as an arrow that goes **back up** to an earlier step. Here is counting down from 3:

```diagram
   ( start ) --> [ n = 3 ] --> < n > 0 ? > --no--> ( end )
                                   | yes  ^
                                   v      |
                              / say n /   |
                                   |      |
                              [ n = n - 1 ]
```

### Flowchart or pseudocode?
Use whichever makes the problem clearer. Flowcharts are good for decisions with several branches and for explaining to people who do not program. Pseudocode is quicker to write and closer to real code. Professionals use both, and many other kinds of diagram.

> In industry: You will rarely draw formal flowcharts at work, but you will constantly sketch boxes and arrows on a whiteboard to agree on how something should behave before anyone writes code.
#Q In a flowchart, what does a diamond shape mean?
- The start of the algorithm
* A decision with a yes/no answer
- An output
! Diamonds hold questions, and have one arrow leaving for each answer.
#Q How does a loop appear in a flowchart?
- As a larger box
- As a dotted line
* As an arrow going back to an earlier step
! Repetition is drawn by returning to a step that has already been done.

#LESSON Breaking big problems into small ones | 12
The most important problem-solving skill in programming is **decomposition**: splitting a problem you cannot solve into smaller problems you can.

"Make a quiz game" is too big to start on. Split it:

```diagram
                    quiz game
        +---------------+----------------+
   load the         ask one            show the
   questions        question           final score
                +------+------+
            show the   read the   check the
            question   answer     answer
```

Each box at the bottom is small enough to write. Solve them one at a time, test each, then join them together.

### Four habits that help
1. **Understand the problem first.** Restate it in your own words. What goes in? What should come out? Work two or three examples by hand.
2. **Solve a simpler version.** Cannot handle a whole list? Handle two numbers. Cannot handle any size of board? Handle 3 by 3.
3. **Look for a pattern** you have seen before. Many problems are an old problem wearing a new coat: finding a largest value, counting things, searching.
4. **Ignore detail that does not matter yet.** This is **abstraction**. When planning the quiz you do not care what colour the buttons are.

### When you are stuck
Say the problem out loud, step by step, to a person or even to a rubber duck on your desk. Explaining forces you to notice the step you skipped. This is a real technique with a real name: **rubber duck debugging**.

> In industry: A senior engineer's first move on a large task is to break it into pieces that can each be built, tested and reviewed separately, often by different people.
#Q What is decomposition?
- Deleting code that is not needed
* Splitting a large problem into smaller, solvable problems
- Making a program run faster
! You solve the small pieces one at a time and then combine them.
#Q You cannot work out how to sort a list of 1,000 names. What is a good next step?
- Give up and search for the answer
- Start typing code and hope
* Work out by hand how you would sort three names, and look for the pattern
! Solving a smaller version reveals the steps you can then generalise.

#LESSON The mathematics programmers use most | 12
You do not need advanced mathematics to begin programming. You need a handful of ideas, used constantly.

### Order of operations
Multiplication and division happen before addition and subtraction. `2 + 3 * 4` is 14, not 20. Use brackets whenever you want a different order or want to make it obvious: `(2 + 3) * 4` is 20.

### Integer division and remainder
Dividing 17 by 5 gives 3 with 2 left over. Programming gives you both parts separately:

- **Integer division** keeps the whole part: 17 divided by 5 is 3.
- The **remainder** (called **modulo**, written `%`) keeps what is left: `17 % 5` is 2.

Modulo is one of the most useful tools you will learn:

| Question | How modulo answers it |
|---|---|
| Is n even? | `n % 2` is 0 |
| Is n divisible by 7? | `n % 7` is 0 |
| What is the last digit of n? | `n % 10` |
| What hour is it 30 hours after 9 o'clock? | `(9 + 30) % 24` is 15 |

That last one shows modulo "wrapping around", like a clock.

### Powers
`2 ** 10` (2 to the power 10) is 1024. Powers of two appear everywhere because of binary: 2, 4, 8, 16, 32, 64, 128, 256, 512, 1024.

### Whole numbers and decimals
Computers store whole numbers (**integers**) exactly. Numbers with a decimal point (**floating-point** numbers) are stored approximately, because most decimals have no exact binary form. That is why a computer may tell you `0.1 + 0.2` is `0.30000000000000004`.

> Warning: Never use floating-point numbers for money. Store amounts as whole numbers of cents.

> In industry: The floating-point surprise above is not a bug in any language. It follows from the IEEE 754 standard that nearly all hardware uses.
#Q What is 17 % 5?
* 2
- 3
- 3.4
! 17 = 3 × 5 + 2, so the remainder is 2.
#Q Which test tells you whether a whole number n is even?
- n / 2 is 0
* n % 2 is 0
- n % 2 is 1
! An even number leaves no remainder when divided by 2.

@solution
def largest(numbers):

    for n in numbers:
        if n > best:

#LESSON Your first program: values and variables | 14
Time to write real code. We use **Python** because it reads almost like English and lets you focus on ideas rather than punctuation.

The traditional first program prints a greeting:

```py
print("Hello, world!")
```

`print` is a **function**: a named action. The text in quotes is a **string**. Run it and the words appear.

### Variables
A **variable** is a name that refers to a value, so you can use the value again later. You create one with `=`, which means "make this name refer to this value":

```py
name = "Ada"
age = 36
print(name)
print(age + 1)
```

Read `age = 36` as "age becomes 36", not "age equals 36". The right side is worked out first, then the name on the left is attached to the result. That is why this makes sense:

```py
score = 10
score = score + 5     # work out 10 + 5, then score becomes 15
```

### Naming

#LESSON Types of data | 14
Every value has a **type**, which says what kind of thing it is and what you can do with it. Python's basic types:

|---|---|---|
| Whole number | `int` | `7`, `-3`, `0` |

```py
print(7 + 7)          # 14

```


#LESSON Making decisions with if | 14
An `if` statement runs some code only when a condition is true.

```py
temperature = 31
if temperature > 30:
    print("It is hot")
    print("Drink water")
print("Done")
```

Two details matter enormously in Python:

1. The line ends with a **colon**.
2. The lines that belong to the `if` are **indented** (four spaces). Indentation is how Python knows which lines are inside. `print("Done")` is not indented, so it always runs.

### if, elif, else
Use `else` for "otherwise", and `elif` (short for "else if") for more choices. Python checks them in order and runs the **first** one that is true, then skips the rest.

```py
score = 72
if score >= 90:
    grade = "A"
elif score >= 80:
    grade = "B"
elif score >= 70:
    grade = "C"
else:
    grade = "F"
print(grade)        # C
```

Order matters. If you tested `score >= 70` first, a score of 95 would get a C.

### Combining conditions

```py
if age >= 18 and has_ticket:
    print("Welcome")
```

### Nesting
An `if` can sit inside another `if`. Each level is indented further. More than two or three levels becomes hard to read, which is a sign the logic should be simplified.

### Truthiness
Python treats some values as false in a condition: `0`, `""` (empty string), empty lists, and `None`. Everything else counts as true. So `if name:` means "if name is not empty".

> In industry: A common review comment is "this condition is hard to follow". Giving a complicated condition a name, such as `is_eligible = age >= 18 and has_ticket`, makes the `if` read like a sentence.

#LESSON Repeating with loops | 16
A **loop** runs the same lines many times. Python has two kinds.

### for: once per item
Use `for` when you know what you are stepping through.

```py
for name in ["Ada", "Alan", "Grace"]:
    print("Hello", name)
```

To repeat a number of times, use `range`:

```py
for i in range(5):
    print(i)            # 0 1 2 3 4
```

`range(5)` starts at 0 and **stops before** 5. `range(1, 6)` gives 1 to 5. `range(0, 10, 2)` counts in twos.

### while: as long as a condition holds
Use `while` when you do not know in advance how many times.

```py
n = 10
while n > 0:
    print(n)
    n = n - 3
```

Something inside a `while` loop must change so the condition eventually becomes false. If nothing does, you have an **infinite loop** and the program never ends.

### The accumulator pattern
The most common loop of all: start with an empty result, add to it each time round.

```py
total = 0
for n in [4, 9, 2]:
    total = total + n
print(total)            # 15
```

The same shape counts things (start at 0, add 1), finds a largest value, or builds a string.

### break and continue
`break` leaves the loop immediately. `continue` skips to the next time round.

### Off-by-one errors
The classic loop bug is running one time too many or too few, usually from forgetting that `range` stops before its end. Test with the smallest cases: zero items, one item.

> In industry: Loops are where programs spend their time. In Stage 2 you will learn to measure how the number of loop steps grows as the data grows, which decides whether a program is fast or unusable.

#LESSON Functions | 15
A **function** is a named block of code that does one job. You have used functions already (`print`, `input`, `int`). Now you will write your own.

```py
def greet(name):
    message = "Hello, " + name + "!"
    return message

```

- `def` starts the definition; `greet` is the name.
- `name` is a **parameter**: a variable that receives a value when the function is called.

This catches almost everyone. `print` shows text on the screen. `return` gives a value back to the program so it can be used.


1. **Reuse.** Write once, call many times.
2. **Naming.** `average(scores)` tells the reader what happens without the detail.
3. **Testing.** A function that takes inputs and returns an output can be checked on its own.
4. **Decomposition.** Each small problem from your plan becomes one function.

```py
def power(base, exponent=2):

```

> Key idea: A good function does one thing, and its name says what that thing is.

#LESSON Scope: where variables live | 10
Variables created inside a function exist only while that function runs. They are **local** to it. This is called **scope**.

```py
def add_tax(price):
    tax = price * 0.13
    return price + tax

print(add_tax(100))    # 113.0
print(tax)             # NameError: tax is not defined
```

`tax` belongs to `add_tax`. When the function returns, `tax` is gone. Two different functions can both use a variable called `total` without interfering with each other. That is the whole point: you can write and understand each function on its own.

A variable created outside every function is **global**. Functions can read it:

```py
RATE = 0.13

def add_tax(price):
    return price + price * RATE
```

Reading a global constant like this is fine. *Changing* global variables from inside functions is a habit to avoid, because then the result of a function depends on hidden state and on what ran before, and the program becomes hard to reason about.

> Key idea: Give a function everything it needs through its parameters, and get everything back through its return value. Then you can understand it by reading only its own lines.

### How a call works
Each time a function is called, Python creates a fresh workspace (a **stack frame**) holding its parameters and local variables. When the function returns, that workspace is thrown away. This is why each call starts clean.

```diagram
  calling add_tax(100)
  +--------------------------+
  | add_tax frame            |
  |   price = 100            |   <- exists only during the call
  |   tax   = 13.0           |
  +--------------------------+
  | main program             |
  |   RATE = 0.13            |
  +--------------------------+
```

> In industry: Functions that depend only on their inputs are called **pure**. They are the easiest code to test and to trust, and experienced engineers push as much logic as possible into them.
#Q A variable is created inside a function. Where can it be used?
* Only inside that function
- Anywhere in the program
- Only in other functions
! It is local, and disappears when the function returns.
#Q Why is changing global variables from inside functions discouraged?
- It is slower
- Python forbids it
* The function's behaviour then depends on hidden state, which makes programs hard to understand
! Parameters in, return value out, keeps each function understandable on its own.

#LESSON Lists | 15
A **list** holds many values in order. It is Python's version of what most languages call an array.

```py
scores = [72, 85, 90]
print(scores[0])        # 72
print(len(scores))      # 3
```

Each position has a number called an **index**, and **indexes start at 0**. A list of 3 items has indexes 0, 1 and 2. Asking for `scores[3]` is an `IndexError`. Negative indexes count from the end: `scores[-1]` is the last item.

### Changing a list
Lists are **mutable**: they can be changed in place.

```py
scores.append(64)       # add to the end
scores[0] = 75          # replace an item
scores.remove(90)       # remove the first 90
last = scores.pop()     # remove and return the last item
```

### Looping

```py
for s in scores:
    print(s)

for i in range(len(scores)):          # when you need the position
    print(i, scores[i])
```

### Slicing
`scores[1:3]` gives a new list with items at index 1 and 2 (it stops before 3). `scores[:2]` is the first two; `scores[2:]` is everything from index 2.

### Useful built-ins
`sum(scores)`, `min(scores)`, `max(scores)`, `sorted(scores)`, and `x in scores`, which is `True` if x is in the list.

### One list, two names
A variable holds a reference to a list, not a copy of it.

```py
a = [1, 2, 3]
b = a            # b refers to the SAME list
b.append(4)
print(a)         # [1, 2, 3, 4]
```

To get a separate copy, write `b = a.copy()`.

> In industry: "It changed and I did not touch it" is very often two names for one list. Understanding references early saves hours of confusion later.

#LESSON Strings in depth | 12
A string is a sequence of characters, and much of what works on lists works on strings too.

```py
word = "Python"
print(word[0])        # P
print(word[-1])       # n
print(word[0:3])      # Pyt
print(len(word))      # 6
for ch in word:
    print(ch)
```

One big difference: strings are **immutable**. You cannot change a character in place. Methods that seem to change a string actually return a *new* one:

```py
name = "ada"
name.upper()           # makes "ADA" and then throws it away
name = name.upper()    # keeps it
```

### Methods you will use constantly

| Method | What it does | Example | Result |
|---|---|---|---|
| `lower()`, `upper()` | change case | `"Hi".lower()` | `"hi"` |
| `strip()` | remove spaces from both ends | `"  hi ".strip()` | `"hi"` |
| `replace(a, b)` | swap every a for b | `"cat".replace("c", "b")` | `"bat"` |
| `split()` | break into a list of words | `"a b c".split()` | `["a", "b", "c"]` |
| `join(list)` | glue a list into a string | `"-".join(["a", "b"])` | `"a-b"` |
| `find(s)` | index of s, or -1 | `"hello".find("l")` | `2` |
| `startswith(s)` | True or False | `"hello".startswith("he")` | `True` |

And `"ell" in "hello"` is `True`.

### Cleaning input
Text typed by people is messy: stray spaces, mixed capitals. A standard first step is to normalise it:

```py
answer = input("Continue? ").strip().lower()
if answer == "yes":
    print("Continuing")
```

Methods can be chained like this because each returns a new string.

### Building strings in a loop

```py
result = ""
for ch in "hello":
    result = ch + result
print(result)             # olleh
```

> In industry: A large part of real programming is text processing: reading files, cleaning user input, parsing data from other systems. These few methods do most of that work.

#LESSON Dictionaries | 12
A list finds things by position. A **dictionary** finds things by **key**, like looking up a word to find its meaning.

```py
ages = {"Ada": 36, "Alan": 41}
print(ages["Ada"])        # 36
ages["Grace"] = 85        # add a new pair
ages["Ada"] = 37          # change a value
print(len(ages))          # 3
```

Each entry is a **key: value** pair. Keys must be unique; values can be anything, including lists or other dictionaries.

Looking up a key that is not there is a `KeyError`. Two safe ways to check:

```py
if "Linus" in ages:
    print(ages["Linus"])

print(ages.get("Linus", 0))     # 0, the default you chose
```

### Looping

```py
for name in ages:                    # keys
    print(name, ages[name])

for name, age in ages.items():       # keys and values together
    print(name, age)
```

### The counting pattern
Dictionaries are perfect for counting how often things occur.

```py
counts = {}
for ch in "banana":
    counts[ch] = counts.get(ch, 0) + 1
print(counts)        # {'b': 1, 'a': 3, 'n': 2}
```

### Structured data
A dictionary can describe one thing with named fields, and a list of dictionaries describes many:

```py
books = [
    {"title": "Dune", "year": 1965},
    {"title": "Emma", "year": 1815},
]
for book in books:
    print(book["title"])
```

This shape, lists of records with named fields, is how most data moves between programs. The format called **JSON** that web services exchange looks almost exactly like it.

> In industry: Dictionary lookup is extremely fast no matter how many entries there are. Stage 2 explains why (the hash table) and when that makes a dictionary the right tool.

#LESSON Debugging: finding your own mistakes | 14
Every programmer writes bugs, every day. The skill is not avoiding them completely; it is finding them quickly. **Debugging** is detective work, and it can be learned.

### Three kinds of error
1. **Syntax errors.** The code breaks the language's grammar, so it will not start. The message names a line. The real mistake is often on that line or the one just before (a missing bracket or colon).
2. **Runtime errors.** The program starts, then stops with an error: `NameError`, `TypeError`, `IndexError`, `KeyError`, `ZeroDivisionError`.
3. **Logic errors.** The program runs and gives the wrong answer. No message. These are the hard ones.

### Read the error message
Python tells you the **kind** of error, a **description**, and the **line number**. Beginners skip it; professionals read it first. Read the last line, which says what went wrong, then find the line number in your own code.

### A method that works
1. **Reproduce it.** Find an input that causes the problem every time.
2. **State what you expected and what happened.** Exactly.
3. **Form a guess** about the cause.
4. **Test the guess.** The simplest tool is `print`: show the values of variables at key points and compare them with what you believed they were.
5. **Fix the cause**, not the symptom, then run the failing input again, and a few others.

```py
def average(numbers):
    total = 0
    for n in numbers:
        total = n               # bug
    print("total is", total)    # debugging print reveals it
    return total / len(numbers)
```

### Halve the search
If you do not know where the problem is, check the values halfway through. If they are right there, the bug is later; if wrong, earlier. Repeat. This finds a bug in a thousand lines in about ten checks.

> Key idea: When a program misbehaves, something you believe about it is false. Debugging is finding out which belief.

> In industry: Teams keep a failing example as an automated test after fixing a bug, so the same bug can never return unnoticed. You will learn to write such tests in Stage 2.

@solution
def clean(text):
    return text.strip().lower()


def longest_word(text):
    best = ""
    for word in text.split():
        if len(word) > len(best):
            best = word
    return best


def letter_counts(text):
    counts = {}
    for ch in text.lower():
        if ch in "abcdefghijklmnopqrstuvwxyz":
            counts[ch] = counts.get(ch, 0) + 1
    return counts


def is_palindrome(text):
    letters = ""
    for ch in text.lower():
        if ch != " ":
            letters += ch
    return letters == letters[::-1]

@solution

    return result
