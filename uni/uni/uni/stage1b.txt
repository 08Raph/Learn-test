#LESSON A second language: JavaScript | 12
You can already program. Variables, conditions, loops, functions, lists and dictionaries exist in almost every language. Learning a second language is mostly learning new spelling for ideas you know, and seeing which parts were Python and which parts were *programming*.

**JavaScript** is the language that runs inside every web browser. It is also used on servers. It has nothing to do with Java beyond the name.

```js
let name = "Ada";
const year = 1843;
console.log("Hello, " + name);
```

What changed from Python:

| Idea | Python | JavaScript |
|---|---|---|
| Create a variable | `x = 5` | `let x = 5;` |
| A value that never changes | (by convention) | `const x = 5;` |
| Print | `print(x)` | `console.log(x);` |
| Blocks | indentation | curly brackets `{ }` |
| End of statement | new line | semicolon `;` |
| Comment | `# note` | `// note` |
| True, false, nothing | `True False None` | `true false null` |

### let and const
Use `const` by default. It promises the name will not be re-assigned, which makes code easier to follow. Use `let` only when the value must change. Avoid the older `var`.

### Types
JavaScript has `number` (one type for whole and decimal numbers), `string`, `boolean`, plus `null` and `undefined`. A variable that was declared but never given a value is `undefined`.

### Equality
Always compare with `===` and `!==`. The two-character `==` converts types before comparing and produces surprises: `"5" == 5` is true.

```js
console.log(5 === 5);       // true
console.log("5" === 5);     // false
```

> In industry: JavaScript is the only language browsers run natively, so every web developer needs it. TypeScript, which you meet in Stage 2, is JavaScript with types added.

#LESSON Conditions, loops and functions in JavaScript | 14
The ideas are the ones you know. Only the punctuation is new: conditions go in round brackets and blocks in curly brackets.

```js
const score = 72;
if (score >= 90) {
  console.log("A");
} else if (score >= 70) {
  console.log("C");
} else {
  console.log("F");
}
```

Logical operators are symbols: `&&` is and, `||` is or, `!` is not.

### Loops

```js
for (let i = 0; i < 5; i++) {     // start; keep going while; step
  console.log(i);
}

for (const name of ["Ada", "Alan"]) {
  console.log(name);
}

let n = 10;
while (n > 0) {
  n -= 3;
}
```

The three-part `for` packs a counting loop into one line: where to start, the condition to continue, and what to do after each pass. `i++` means "add 1 to i".

### Functions

```js
function area(width, height) {
  return width * height;
}
```

JavaScript also has a shorter form, the **arrow function**, which is very common:

```js
const area = (width, height) => width * height;
const greet = (name) => {
  const message = "Hello, " + name;
  return message;
};
```

With a single expression and no curly brackets, the value is returned automatically. With curly brackets you must write `return`.

### Functions are values
In JavaScript a function can be stored in a variable, put in a list, or handed to another function. That last idea is used everywhere:

```js
const numbers = [1, 2, 3];
const doubled = numbers.map((n) => n * 2);      // [2, 4, 6]
```

`map` calls the function you give it once for each item and collects the results.

> Key idea: Passing a function to another function is how JavaScript says "here is what to do later" or "here is what to do with each item".

#LESSON Arrays and objects | 14
JavaScript's **array** is Python's list. Its **object** is close to Python's dictionary.

### Arrays

```js
const scores = [72, 85, 90];
console.log(scores[0]);        // 72
console.log(scores.length);    // 3
scores.push(64);               // add to the end
const last = scores.pop();     // remove from the end
```

Note that `const` stops you re-assigning the name `scores`. It does not stop you changing the contents of the array.

Three array methods do most everyday work, and each takes a function:

```js
const nums = [1, 2, 3, 4, 5, 6];
const evens = nums.filter((n) => n % 2 === 0);      // [2, 4, 6]
const squares = nums.map((n) => n * n);             // [1, 4, 9, 16, 25, 36]
const total = nums.reduce((sum, n) => sum + n, 0);  // 21
```

- `filter` keeps the items for which the function returns true.
- `map` transforms each item.
- `reduce` combines all items into one value, starting from the second argument.

### Objects
An object groups named values, called **properties**.

```js
const book = { title: "Dune", year: 1965 };
console.log(book.title);          // Dune
book.pages = 412;                 // add a property
console.log(book["year"]);        // 1965  (the bracket form also works)
```

Asking for a property that does not exist gives `undefined`, not an error.

### Arrays of objects
This is the shape of most real data:

```js
const books = [
  { title: "Dune", year: 1965 },
  { title: "Emma", year: 1815 },
];
const old = books.filter((b) => b.year < 1900).map((b) => b.title);   // ["Emma"]
```

### JSON
**JSON** (JavaScript Object Notation) is this same notation used as a text format for sending data between programs. `JSON.stringify(book)` turns an object into text; `JSON.parse(text)` turns text back into an object.

> In industry: Almost every web service sends and receives JSON. Reading a JSON response and picking out the fields you need with `filter` and `map` is daily work.

#LESSON The page as a tree: the DOM | 12
When a browser loads a web page it builds a model of it in memory called the **DOM** (Document Object Model). The DOM is a tree: the page contains a body, the body contains headings and paragraphs, and so on. JavaScript can read and change that tree, and the screen updates immediately.

```diagram
            document
               |
             <html>
          +----+-----+
       <head>      <body>
          |      +----+----+
       <title>  <h1>      <ul>
                        +--+--+
                      <li>   <li>
```

### Finding elements

```js
const title = document.querySelector("h1");            // the first match
const items = document.querySelectorAll("li");         // every match
const box = document.querySelector("#message");        // the element with id="message"
```

The text inside the brackets is a **CSS selector**, the same notation used for styling: a tag name, `#id`, or `.class`.

### Changing them

```js
title.textContent = "Welcome back";      // change the text
box.classList.add("warning");            // add a CSS class
box.style.color = "red";                 // change one style directly
```

### Creating new elements

```js
const li = document.createElement("li");
li.textContent = "Buy milk";
document.querySelector("ul").appendChild(li);
```

Create the element, fill it in, then attach it to the tree. Until you attach it, it exists only in memory and is not visible.

> Warning: Use `textContent` to insert text that came from a user. Its cousin `innerHTML` treats the text as page code, which lets an attacker inject their own script. This kind of attack is called cross-site scripting and you will study it in Stage 3 and Stage 4.

> In industry: Large applications use libraries such as React that update the DOM for you. They are built on exactly these operations, and understanding the DOM is what lets you debug them.
#Q What is the DOM?
- A programming language
* The browser's in-memory tree model of the page
- A kind of web server
! JavaScript reads and changes this tree, and the browser redraws the page.
#Q Why prefer textContent over innerHTML for text typed by a user?
- It is shorter to type
* innerHTML would run any page code hidden in the text
- textContent is faster to display
! Treating untrusted text as HTML allows script injection.

#LESSON Events: reacting to the user | 12
A web page mostly waits. Code runs when something happens: a click, a key press, a form being submitted. Each such happening is an **event**, and the function you want run is an **event listener**.

```js
const button = document.querySelector("#save");
button.addEventListener("click", () => {
  console.log("Saved!");
});
```

Read it as: "when this button is clicked, call this function". You are not calling the function yourself. You are handing it to the browser to call later. This style is called **event-driven programming**.

### A complete example

```html
<p>Clicks: <span id="count">0</span></p>
<button id="add">Add one</button>
```

```js
let clicks = 0;
const out = document.querySelector("#count");
document.querySelector("#add").addEventListener("click", () => {
  clicks += 1;
  out.textContent = clicks;
});
```

Notice the pattern that every interactive page follows:

1. Keep the **state** (here, `clicks`) in variables.
2. When an event happens, **update the state**.
3. **Redraw** the part of the page that shows it.

### Useful events
`click`, `input` (text in a box changed), `submit` (a form was sent), `keydown` (a key was pressed).

### The event object
The listener receives an object describing what happened:

```js
input.addEventListener("input", (event) => {
  console.log(event.target.value);       // the current text in the box
});
```

`event.target` is the element the event happened on. For forms, call `event.preventDefault()` to stop the browser reloading the page.

> Key idea: State, event, update, redraw. Every user interface you will ever build, in any technology, is some version of this loop.
#Q What does addEventListener("click", fn) do?
- Runs fn immediately
* Asks the browser to call fn each time the element is clicked
- Clicks the element
! You register the function; the browser calls it when the event occurs.
#Q In the state, event, update, redraw pattern, what is "state"?
- The CSS of the page
* The data the program remembers, such as a counter
- The internet connection
! State is the information that changes over time and decides what the page shows.

#LAB js | To-do list logic
Write the logic of a to-do list as plain functions, separate from any page. Each task is an object like `{ text: "Buy milk", done: false }`.

- `addTask(tasks, text)` returns a **new** array with a new, not-done task added at the end. If `text` is empty or only spaces, return the list unchanged. Trim spaces from the text.
- `toggleTask(tasks, index)` returns a new array where the task at `index` has its `done` value flipped. Other tasks are unchanged.
- `remaining(tasks)` returns how many tasks are not done.

Do not change the array you are given: build and return a new one. Keeping logic in pure functions like this is what makes it testable.
@starter
function addTask(tasks, text) {
  return tasks;
}

function toggleTask(tasks, index) {
  return tasks;
}

function remaining(tasks) {
  return 0;
}
@solution
function addTask(tasks, text) {
  const clean = text.trim();
  if (clean === "") return tasks;
  return tasks.concat([{ text: clean, done: false }]);
}

function toggleTask(tasks, index) {
  return tasks.map((task, i) => (i === index ? { text: task.text, done: !task.done } : task));
}

function remaining(tasks) {
  return tasks.filter((task) => !task.done).length;
}
@tests
addTask([], "Buy milk") => [{"text": "Buy milk", "done": false}]
addTask([{ text: "a", done: true }], "  b  ") => [{"text": "a", "done": true}, {"text": "b", "done": false}]
addTask([], "   ") => []
addTask([{ text: "a", done: false }], "") => [{"text": "a", "done": false}]
toggleTask([{ text: "a", done: false }, { text: "b", done: false }], 1) => [{"text": "a", "done": false}, {"text": "b", "done": true}]
toggleTask([{ text: "a", done: true }], 0) => [{"text": "a", "done": false}]
remaining([{ text: "a", done: true }, { text: "b", done: false }, { text: "c", done: false }]) => 2
remaining([]) => 0
((t) => { addTask(t, "x"); return t.length; })([]) => 0
@hints
`text.trim()` removes spaces from both ends. Check for the empty string after trimming.
`tasks.concat([newTask])` returns a new array and leaves the original alone. `push` would change the original.
`map` gives you each task and its index. Return a new object for the one you are toggling and the same object for the rest.
`filter` then `.length` counts the tasks that match a condition.

#LESSON How the web works, and your first page | 12
When you visit a website, your browser (the **client**) sends a request across the internet to another computer (the **server**). The server sends back files. The browser reads them and draws the page.

```diagram
   your browser   ---- "please send /index.html" ---->   web server
    (client)      <---- the HTML file (then CSS, JS) ----
```

Three languages make up a page, each with one job:

| Language | Job | Comparison |
|---|---|---|
| **HTML** | What is on the page: structure and content | The skeleton |
| **CSS** | How it looks | Skin and clothes |
| **JavaScript** | What it does | Muscles |

**HTML** (HyperText Markup Language) is not a programming language. It has no loops or conditions. It *marks up* content with **tags** that say what each piece is.

```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <title>My first page</title>
  </head>
  <body>
    <h1>Hello</h1>
    <p>This is a <strong>paragraph</strong>.</p>
  </body>
</html>
```

Most elements have an **opening tag** `<p>`, some content, and a **closing tag** `</p>`. Elements nest inside each other, which forms the tree you met as the DOM.

- `<!doctype html>` tells the browser this is modern HTML.
- `<head>` holds information *about* the page, not shown in the page itself. `<title>` is the text on the browser tab.
- `<body>` holds everything the visitor sees.

A tag can have **attributes** that give extra information, written as `name="value"`, such as `lang="en"` above.

> In industry: Browsers are very forgiving of broken HTML and will display something anyway. That makes mistakes easy to miss, which is why teams run validators and linters on their pages.

! HTML says what things are; CSS says how they look; JavaScript says what they do.
#Q Where does the text shown on the browser tab come from?
- The first h1
* The title element inside head
- The file name
! `<title>` sets the tab text and the name used in bookmarks and search results.

#LESSON The elements you need most | 14
A small set of elements builds almost any page.

### Text
`<h1>` to `<h6>` are headings, from most to least important. Use one `<h1>` per page and do not skip levels. `<p>` is a paragraph. `<strong>` marks importance and `<em>` marks emphasis.

### Links and images

```html
<a href="https://example.com">Visit Example</a>
<img src="cat.jpg" alt="A grey cat asleep on a windowsill">
```

`href` is where the link goes. `src` is the image file. `alt` is text that describes the image for people who cannot see it and for when the image fails to load. Always write it. `<img>` has no closing tag because it has no content.

### Lists

```html
<ul>
  <li>Milk</li>
  <li>Eggs</li>
</ul>
```

`<ul>` is an unordered (bulleted) list; `<ol>` is ordered (numbered). Each item is an `<li>`.

### Forms

```html
<form>
  <label for="email">Email</label>
  <input id="email" type="email" required>
  <button type="submit">Sign up</button>
</form>
```

Every input needs a `<label>`. The label's `for` matches the input's `id`, which connects them: clicking the label focuses the box, and screen readers read the label aloud.

### Semantic structure
Rather than making everything a plain box, HTML has elements that say what part of the page something is:

```html
<header>…</header>
<nav>…</nav>
<main>
  <article>…</article>
</main>
<footer>…</footer>
```

These are **semantic** elements: they carry meaning. Browsers, search engines and assistive technology use that meaning. When no semantic element fits, use `<div>` (a block) or `<span>` (a piece of text), which mean nothing by themselves.

> Key idea: Choose an element for what the content *is*, never for how it looks by default. Looks are CSS's job.
#Q Why should every img have an alt attribute?
- It makes the image load faster
* It describes the image for people who cannot see it
- It sets the image size
! Screen readers read the alt text, and it is shown if the image fails to load.
#Q Which element is the right choice for the main navigation links of a site?
- div
* nav
- span
! `<nav>` is the semantic element for navigation.

#LESSON Styling with CSS | 14
**CSS** (Cascading Style Sheets) controls appearance. A stylesheet is a list of **rules**. Each rule has a **selector** that picks elements and **declarations** that style them.

```css
h1 {
  color: navy;
  font-size: 32px;
}
```

Put CSS in a `<style>` element in the head, or better, in a separate file linked with `<link rel="stylesheet" href="style.css">`.

### Selectors

| Selector | Picks |
|---|---|
| `p` | every `<p>` element |
| `.note` | every element with `class="note"` |
| `#intro` | the one element with `id="intro"` |
| `nav a` | every `<a>` inside a `<nav>` |
| `a:hover` | a link while the pointer is over it |

Classes are the workhorse. An element can have several: `class="card featured"`.

### The cascade
When two rules set the same property on an element, which wins? Roughly: the more **specific** selector wins (an id beats a class, a class beats a tag), and between equals, the **later** rule wins. This is the "cascading" in the name. Keeping selectors simple, mostly single classes, avoids fights.

### The box model
Every element is a rectangular box with four layers:

```diagram
  +------------------------------------+
  |            margin                  |   space outside
  |   +----------------------------+   |
  |   |         border             |   |
  |   |   +--------------------+   |   |
  |   |   |      padding       |   |   |   space inside
  |   |   |   +------------+   |   |   |
  |   |   |   |  content   |   |   |   |
  |   |   |   +------------+   |   |   |
  |   |   +--------------------+   |   |
  |   +----------------------------+   |
  +------------------------------------+
```

```css
.card {
  padding: 16px;
  border: 1px solid #ccc;
  margin: 12px;
  border-radius: 8px;
}
```

Add `* { box-sizing: border-box; }` at the top of your stylesheet so that a width you set includes padding and border. Almost every professional stylesheet starts with it.

### Units
`px` is a fixed size. `rem` is relative to the user's chosen text size, so it respects their settings; prefer it for text. `%` is relative to the parent.
#Q Which selector picks every element with class="note"?
- note
* .note
- #note
! A dot selects by class; a hash selects by id.
#Q In the box model, what is padding?
- Space outside the border
* Space between the content and the border
- The thickness of the border
! Padding is inside the border; margin is outside it.

#LESSON Layout with flexbox | 12
By default, block elements stack vertically, one under another. To put things side by side and control the spacing, use **flexbox**.

Set `display: flex` on a **container**, and its direct children become **flex items** laid out in a row.

```css
.toolbar {
  display: flex;
  gap: 12px;                       /* space between items */
  justify-content: space-between;  /* spread along the row */
  align-items: center;             /* line up across the row */
}
```

Two properties do most of the work. Think of a row as having a **main axis** (left to right) and a **cross axis** (top to bottom):

- `justify-content` positions items along the main axis: `flex-start`, `center`, `flex-end`, `space-between`.
- `align-items` positions them on the cross axis: `stretch`, `center`, `flex-start`, `flex-end`.

```diagram
  justify-content: space-between
  +------------------------------------------+
  | [Logo]            [Home] [About] [Login] |   <- align-items: center
  +------------------------------------------+
```

### Growing and wrapping
`flex: 1` on an item tells it to grow and take the spare space. `flex-wrap: wrap` on the container lets items move to a new line when they do not fit.

```css
.cards { display: flex; flex-wrap: wrap; gap: 16px; }
.card  { flex: 1 1 240px; }      /* grow, shrink, start at 240px wide */
```

That one rule makes cards sit three across on a wide screen, two on a tablet and one on a phone, with no further code.

### Columns
`flex-direction: column` stacks items vertically and swaps which axis is which.

### Centring
The old joke was that centring something in CSS was impossible. With flexbox it is three lines:

```css
.hero { display: flex; justify-content: center; align-items: center; }
```

> In industry: Flexbox handles one-dimensional layouts (a row or a column). For two-dimensional layouts such as a whole-page grid, CSS Grid is the companion tool. Real pages use both.
#Q What does display: flex on a container do to its direct children?
- Hides them
* Lays them out as flex items, in a row by default
- Makes them all the same colour
! The children become flex items arranged along the main axis.
#Q Which property spreads items along the main axis?
* justify-content
- align-items
- flex-wrap
! `justify-content` works along the main axis; `align-items` works across it.

#LESSON Responsive and accessible pages | 12
People will open your page on a phone, a tablet, a laptop and a huge monitor. Some will zoom in. Some cannot use a mouse. Some cannot see the screen. A professional page works for all of them.

### Responsive design
First, every page needs this line in its head, or phones will show a shrunken desktop page:

```html
<meta name="viewport" content="width=device-width, initial-scale=1">
```

Then design for the **small screen first** and add layout for larger ones with a **media query**:

```css
.layout { display: flex; flex-direction: column; }

@media (min-width: 700px) {
  .layout { flex-direction: row; }
}
```

The rules inside `@media` apply only when the condition is true. Flexible units help too: `max-width: 100%` on images stops them overflowing, and a `max-width` on text keeps lines a readable length.

### Accessibility
Accessibility means people with disabilities can use what you build. Most of it comes from doing HTML properly:

1. **Use semantic elements.** A real `<button>` works with the keyboard and screen readers automatically. A clickable `<div>` does neither.
2. **Write alt text** for images that carry meaning.
3. **Label every form control.**
4. **Keep enough contrast** between text and background.
5. **Make everything reachable by keyboard.** Press Tab through your page. Can you reach and operate everything? Can you see where you are?
6. **Do not rely on colour alone** to carry meaning. Add text or an icon.

> Key idea: Accessibility is not an extra feature. It is part of the page working correctly.

### Testing your page
Narrow the browser window and watch the layout. Use the device toolbar in your browser's developer tools. Tab through with the keyboard. Zoom to 200%.

> In industry: Many countries have laws requiring accessible websites, and the Web Content Accessibility Guidelines (WCAG) are the standard teams are measured against.

* Applies CSS rules only when a condition such as screen width is met
- Loads a different HTML file
! Media queries adapt the layout to the screen.
#Q Why use a button element instead of a clickable div?
- It looks better by default
* A button already works with the keyboard and assistive technology
- Divs cannot be clicked
! Semantic elements bring built-in behaviour and meaning.

#LESSON Combining commands | 10
The real power of the shell is that small commands can be joined.

### Redirection
Normally a command prints to the screen. `>` sends its output to a file instead, and `>>` adds to the end of a file:

```text
ls > files.txt          # save the listing (replacing the file)
echo "done" >> log.txt  # add a line to the end
```

### Pipes
The pipe `|` feeds the output of one command into the input of the next:

```text
cat names.txt | sort | uniq | wc -l
```

Read it left to right: print the names, sort them, remove duplicates, count the lines. Four tiny tools, one answer: how many different names are in the file.

| Tool | Does |
|---|---|
| `grep word file` | show lines containing word |
| `sort` | sort lines |
| `uniq` | drop repeated neighbouring lines |
| `wc -l` | count lines |
| `head -n 5` | first 5 lines |
| `tail -n 5` | last 5 lines |

Finding every line with "error" in a log and counting them:

```text
grep error server.log | wc -l
```

### Scripts
Put commands in a file and you have a **script**: a program made of shell commands.

```text
#!/usr/bin/env bash
mkdir -p backup
cp *.txt backup/
echo "Backed up"
```

`*.txt` is a **wildcard** meaning "every name ending in .txt". The first line tells the system which program should run the script.

### Environment variables
The shell keeps named settings such as `PATH` (the folders searched for commands) and `HOME`. `echo $HOME` prints one. Programs read them for configuration.

> Key idea: Small programs that each do one thing, joined by text streams. This idea, the "Unix philosophy", shaped how good software is designed far beyond the terminal.

> In industry: Deployment, builds and data clean-up are automated with scripts like these. A task you would do by hand twice is a task worth scripting.

#LESSON Git: saving the history of your work | 14
Imagine files named `essay_final.doc`, `essay_final2.doc`, `essay_REALLY_final.doc`. **Version control** replaces that mess. It records snapshots of your project so you can see what changed, when and why, and go back to any earlier state. The standard tool is **Git**.

### The three areas
Git tracks your work in three places, and understanding them removes most confusion:

```diagram
  working folder   --- git add --->   staging area   --- git commit --->   repository
  (files you edit)                    (what will go                        (permanent
                                       into the next                        history of
                                       snapshot)                            snapshots)
```

A **repository** (repo) is a project folder plus its full history. A **commit** is one snapshot, with a message explaining it.

### The everyday cycle

```text
git init                       # start tracking this folder (once)
git status                     # what has changed?
git add index.html             # stage a file
git commit -m "Add home page"  # save the snapshot
git log --oneline              # view the history
```

`git status` is the command you will run most. It tells you exactly what state things are in and often suggests what to do next.

### What makes a good commit
- **Small and focused**: one logical change.
- **A clear message** in the imperative: "Fix login error for empty password", not "stuff" or "changes".

Future you, searching for when a bug appeared, will be grateful.

### Seeing and undoing
`git diff` shows what you changed since the last commit. `git restore file` throws away uncommitted changes to a file. Because every commit is kept, almost nothing committed is ever truly lost.

### What not to commit
A file named `.gitignore` lists things Git should leave out: generated files, downloaded packages, and above all **secrets** such as passwords and keys.

> Warning: A secret committed to a repository stays in its history even after you delete the file. Treat any secret that was ever committed as leaked and replace it.

#Q What does `git add` do?

* Puts changes in the staging area, ready for the next commit

#LESSON Planning before you type | 12
Small exercises tell you exactly what to write. Projects do not, and that is the hard part. Most beginners fail projects not because the code is difficult but because they start typing before they know what they are building.

A plan for a small project fits on one page.

### 1. One sentence
"A calculator that reads an expression like `12 * 4` and prints the answer." If you cannot write the sentence, you do not understand the project yet.

### 2. What it must do
List the features as things a user can do. Mark each **must**, **should** or **could**. Build the musts first. Most abandoned projects died trying to build the coulds.

### 3. Walk through one use
Write down exactly what the user sees and types in one complete run. This small script uncovers questions you had not thought of: what happens on bad input? How does the user quit?

### 4. Break it into functions
Apply decomposition. For each function write its name, what goes in and what comes out. Do not write the bodies yet.

```text
read_expression()            -> text typed by the user
parse(text)                  -> (number, operator, number) or None
calculate(a, operator, b)    -> number
main()                       -> the loop that ties them together
```

### 5. Order of work
Build the smallest thing that runs end to end, even if it does almost nothing. Then grow it one feature at a time, running it after each step. A program that works at every stage is never far from working.

> Key idea: Always have a working program. Add one small thing, run it, see it work, then add the next. Large untested leaps are where projects get lost.

### 6. Decide what "done" means
Write the checks you will run at the end. This becomes your test list.

> In industry: Teams call the smallest end-to-end version a "walking skeleton" or a "minimum viable product". Shipping it early and improving it is the normal way software is built.

- The most interesting feature
* The smallest version that runs end to end

#LESSON Guided build: calculator and guessing game | 14
Two console projects, built the way the last lesson described. Read the walkthrough, then build each yourself without copying.

### Calculator
**Sentence:** read an expression such as `12 * 4`, print the result, repeat until the user types `quit`.

**Step 1: the skeleton.** A loop that reads a line and echoes it back, and stops on `quit`. Run it.

**Step 2: parsing.** Split the line on spaces into three parts. If there are not exactly three, report an error. Convert the first and third to numbers; if that fails, report an error.

```py
def parse(text):
    parts = text.split()
    if len(parts) != 3:
        return None
    try:
        return float(parts[0]), parts[1], float(parts[2])
    except ValueError:
        return None
```

`try` and `except` are how Python handles an error without stopping: attempt the conversion, and if it raises `ValueError`, run the `except` block instead.

**Step 3: calculating.** A function that takes two numbers and an operator and returns the result. It has no `print` and no `input`, so it can be tested alone. Decide what it does for division by zero.

**Step 4: join them** in the loop and try your test list: normal cases, negative numbers, decimals, division by zero, nonsense.

### Number guessing game
**Sentence:** the computer picks a number from 1 to 100; the player guesses until right, with "too high" or "too low" hints.

The structure is a `while` loop that continues until the guess is correct, with a counter. The design decisions are the interesting part:

- What if the player types letters? Use the same `try`/`except` idea and ask again without counting the attempt.
- Should there be a maximum number of guesses?
- With good play, how many guesses are needed at most? Always guessing the middle of the remaining range halves it each time, so seven guesses are enough for 100 numbers. You have just discovered **binary search**, which you will study formally in Stage 2.

> In industry: Separating "work out the answer" from "talk to the user" is the first step toward every architecture pattern you will learn later. The talking part changes often; the logic should not have to.
#Q Why should the calculate function contain no print or input?
- It would run slower
* So it can be tested on its own and reused with a different interface
- Python does not allow it
! Logic that only takes values and returns values is easy to test and reuse.
#Q What does try / except do?
- Repeats code until it works
* Runs code and, if a named error occurs, runs the except block instead of crashing
- Hides all errors permanently
! It lets the program recover from an expected error.

### To-do application (browser)
**State:** an array of task objects. Everything shown on the page is derived from it.

**The loop:** an event changes the state, then one `render` function redraws the whole list from the state. Redrawing everything is simpler and less error-prone than trying to edit the page piece by piece.

```js
let tasks = load();

function render() {
  const list = document.querySelector("#list");
  list.innerHTML = "";
  tasks.forEach((task, index) => {
    const li = document.createElement("li");
    li.textContent = task.text;
    if (task.done) li.classList.add("done");
    li.addEventListener("click", () => { tasks = toggleTask(tasks, index); save(); render(); });
    list.appendChild(li);
  });
}
```

**Saving:** browsers provide `localStorage`, a small key-value store that survives reloads. It only holds strings, so convert with JSON:

```js
const save = () => localStorage.setItem("tasks", JSON.stringify(tasks));
const load = () => JSON.parse(localStorage.getItem("tasks") || "[]");
```

### Command-line notes tool
The same idea outside the browser. The program starts, **reads** a file into memory, makes a change, **writes** the file back, and exits.

```py
import json, sys

def load():
    try:
        with open("notes.json") as f:
            return json.load(f)
    except FileNotFoundError:
        return []

def save(notes):
    with open("notes.json", "w") as f:
        json.dump(notes, f)
```

`sys.argv` is the list of words typed on the command line, so `python notes.py add "Buy milk"` gives `["notes.py", "add", "Buy milk"]`. Check its length before using it and print a usage message if it is wrong.

### The shared lesson
Both programs have the same three layers: **storage** (load, save), **logic** (add, toggle, list) and **interface** (the page or the command line). Keep them apart and you can change one without touching the others.

> In industry: This is the seed of "layered architecture", which you will study in Stage 3. Replace the file with a database and the page with a mobile app, and the logic layer should not need to change.

- The HTML that was there before
* The state: the array of tasks
- The contents of localStorage only
! State is the single source of truth; the page is redrawn from it.
#Q Why is JSON.stringify needed when saving to localStorage?
- To compress the data
* localStorage stores only strings
- To encrypt the data
! Objects and arrays must be converted to text first.

### Test it like a stranger would
You know how your program is supposed to be used, so you unconsciously use it correctly. Deliberately do the wrong things:

- Empty input. Very long input. Letters where numbers belong.
- The first and last item of every list.
- Doing things in an unexpected order, or twice.

Write the cases down with the expected result. Run them again after every change, because fixing one thing often breaks another. (An automated way to do this is coming in Stage 2.)

### Read your own code
Leave it for a day, then read it from top to bottom as if someone else wrote it.

- Is any name unclear? Rename it.
- Is any function doing two jobs? Split it.
- Is the same code written twice? Make it a function.
- Is there code that is no longer used? Delete it.

Improving code's structure without changing what it does is called **refactoring**.

### Write the README
Four short sections are enough:

1. **What it is**, in one or two sentences.
2. **How to run it**, exact commands.
3. **How to use it**, with an example.
4. **What you learned**, and what you would do next.

### Show it
Put it on GitHub and add a card to your personal site. Explaining a project to someone, in writing or aloud, is the best test of whether you understand it.

### Reflect
After each project, write three lines: what went well, what was hard, what you will do differently. People who do this improve much faster than people who simply start the next project.

#LAB js | Calculator engine
Write the logic of a calculator as pure functions, with no input or output.

- `parse(text)` takes text such as `"12 * 4"` and returns an array `[12, "*", 4]`. The three parts are separated by spaces. Extra spaces at the ends or between parts are allowed. If the text does not have exactly three parts, or either number is not a valid number, or the operator is not one of `+ - * /`, return `null`.
- `calculate(a, op, b)` returns the result of the operation. Dividing by zero returns `null`.
- `evaluate(text)` combines them: it returns the numeric result, or the string `"error"` if the text cannot be parsed or the result is `null`.
@starter

  return null;
}

function calculate(a, op, b) {
  return null;
}

function evaluate(text) {
  return "error";
}
@solution
function parse(text) {
  const parts = text.trim().split(/\s+/);
  if (parts.length !== 3) return null;
  const a = Number(parts[0]), b = Number(parts[2]);
  if (parts[0] === "" || Number.isNaN(a) || Number.isNaN(b)) return null;
  if (!["+", "-", "*", "/"].includes(parts[1])) return null;
  return [a, parts[1], b];
}

function calculate(a, op, b) {
  if (op === "+") return a + b;
  if (op === "-") return a - b;
  if (op === "*") return a * b;
  if (op === "/") return b === 0 ? null : a / b;
  return null;
}

function evaluate(text) {
  const p = parse(text);
  if (p === null) return "error";
  const r = calculate(p[0], p[1], p[2]);
  return r === null ? "error" : r;
}
@tests

parse("  3   +  5 ") => [3, "+", 5]
parse("1.5 - 2") => [1.5, "-", 2]

parse("a + 4") => null
parse("3 ^ 4") => null

calculate(6, "/", 0) => null

evaluate("hello") => "error"
evaluate("10 - 2.5") => 7.5
@hints
`text.trim().split(/\s+/)` splits on any run of spaces, so extra spaces do not create empty parts.
`Number("abc")` gives `NaN`. Test it with `Number.isNaN(value)`, because `NaN === NaN` is false.
Check the operator against a list of the four allowed symbols.
`evaluate` should not repeat any logic: call `parse`, then `calculate`, and turn `null` into `"error"`.
