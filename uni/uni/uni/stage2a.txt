#LESSON Classes and objects | 14
In Stage 1 you kept data in variables and behaviour in functions, separately. That works until a program has many related pieces: a bank account has a balance *and* rules about what may happen to it. **Object-oriented programming** (OOP) keeps the data and the functions that work on it together.

A **class** is a blueprint. An **object** (or **instance**) is one thing built from it.

```py
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount

a = Account("Ada", 100)
b = Account("Alan")
a.deposit(50)
print(a.balance, b.balance)     # 150 0
```

- `__init__` is the **constructor**. It runs when an object is created and sets up its starting state.
- `self` is the object being worked on. `a.deposit(50)` calls `deposit` with `self` being `a`.
- `owner` and `balance` are **attributes** (also called fields): data belonging to one object.
- `deposit` is a **method**: a function that belongs to the class.

Each object has its own attributes. Changing `a.balance` does nothing to `b`.

```diagram
        class Account            (the blueprint)
        /              \
   object a          object b    (two separate instances)
   owner "Ada"       owner "Alan"
   balance 150       balance 0
```

### When to make a class
A good class models one **thing** with **state that changes** and **rules about how it may change**. If you only have data, a dictionary may do. If you only have behaviour, a function may do.

> Key idea: An object is state plus the operations allowed on that state.

> In industry: Most large codebases in Java, C#, Python and TypeScript are organised into classes. Reading a class to learn what it is responsible for is an everyday task.

#LESSON Encapsulation | 12
What stops someone writing `a.balance = -500`? Nothing, in the class from the last lesson. **Encapsulation** means an object protects its own state: the outside world may change it only through methods that enforce the rules.

```py
class Account:
    def __init__(self, owner):
        self.owner = owner
        self._balance = 0            # leading underscore: internal

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("deposit must be positive")
        self._balance += amount

    def withdraw(self, amount):
        if amount > self._balance:
            raise ValueError("insufficient funds")
        self._balance -= amount

    def balance(self):
        return self._balance
```

A rule that must always be true of an object, here "the balance is never negative", is called an **invariant**. Every method is responsible for keeping it true. Code outside the class never has to check, because it cannot break it.

`raise ValueError(...)` signals an error to the caller. It stops the method immediately, so the invalid change never happens.

### Public and private
- The **public interface** is what other code is meant to use: `deposit`, `withdraw`, `balance`.
- The **implementation** is how it works inside: `_balance`.

In Python the underscore is a convention meaning "do not touch from outside". Java, C# and C++ enforce it with the keyword `private`.

### Why it pays off
1. **Fewer bugs.** Invalid states cannot be created.
2. **Freedom to change.** If you later store the balance in cents, or keep a list of transactions, no outside code breaks, because none of it reached inside.
3. **Easier to understand.** You can use the class knowing only its public methods.

> Key idea: Hide what may change. Expose only what others need.

> In industry: "Who is allowed to change this data, and where are the rules enforced?" is one of the first questions asked in a design review.
#Q What is an invariant?
- A variable that never changes
* A rule about an object's state that must always hold
- A method with no parameters
! For example, "the balance is never negative". Methods must preserve it.
#Q Why hide an object's internal data behind methods?
- To make the program run faster
* So the rules are always enforced and the internals can change without breaking other code
- Because Python requires it
! Encapsulation protects invariants and reduces coupling.

#LESSON Inheritance | 12
Sometimes one kind of thing is a more specific version of another. A savings account *is an* account, with interest added. **Inheritance** lets a new class take everything an existing class has, then add or change parts.

```py
class Account:
    def __init__(self, owner):
        self.owner = owner
        self._balance = 0

    def deposit(self, amount):
        self._balance += amount

    def describe(self):
        return f"{self.owner}: {self._balance}"


class SavingsAccount(Account):
    def __init__(self, owner, rate):
        super().__init__(owner)        # run the parent's setup first
        self.rate = rate

    def add_interest(self):
        self._balance += self._balance * self.rate
```

`SavingsAccount` is the **subclass** (child); `Account` is the **superclass** (parent). A savings account can `deposit` and `describe` without those methods being written again. `super()` reaches the parent's version of a method.

A subclass can **override** a method by defining one with the same name:

```py
    def describe(self):
        return super().describe() + f" at {self.rate:.0%}"
```

### The is-a test
Use inheritance only when the subclass truly *is a* kind of the superclass, in every situation where the superclass is used. A square is a rectangle in geometry, yet a `Square` class that inherits from a `Rectangle` with separate `set_width` and `set_height` breaks code that expects to change one side alone. This is a famous trap.

### Prefer composition for has-a
A car *has an* engine; it is not a kind of engine. Model that by giving the car an engine object as an attribute. This is **composition**.

```py
class Car:
    def __init__(self):
        self.engine = Engine()
```

> Key idea: Inheritance is a strong, permanent link between classes. Reach for composition first and inheritance only when the is-a relationship is real.

> In industry: Deep inheritance trees are widely regarded as a maintenance problem. Modern style favours small classes combined together.
#Q What does a subclass get from its superclass?
- Nothing unless it copies the code
* All of its attributes and methods, which it may extend or override
- Only its name
! Inheritance reuses the parent's definition.
#Q A Car has an Engine. How should this be modelled?
- Car inherits from Engine
- Engine inherits from Car
* Car holds an Engine object as an attribute
! "Has-a" is composition, not inheritance.

#LESSON Polymorphism | 12
**Polymorphism** means "many forms": the same call works on different kinds of object, and each responds in its own way.

```py
class Circle:
    def __init__(self, r):
        self.r = r
    def area(self):
        return 3.14159 * self.r ** 2

class Rectangle:
    def __init__(self, w, h):
        self.w, self.h = w, h
    def area(self):
        return self.w * self.h

shapes = [Circle(1), Rectangle(2, 3)]
for s in shapes:
    print(s.area())
```

The loop does not know or care which kind of shape `s` is. It calls `area()` and the right version runs. Deciding which method to run while the program is running, based on the object's actual class, is **dynamic dispatch**.

Compare the alternative without polymorphism:

```py
if kind == "circle":
    ...
elif kind == "rectangle":
    ...
```

Every new shape means finding and editing every such chain in the program. With polymorphism, adding a `Triangle` class changes no existing code at all. The program is **open to extension without modification**, an idea you will meet again as one of the SOLID principles.

### Duck typing
In Python, anything with an `area()` method works in that loop; the classes need no shared parent. "If it walks like a duck and quacks like a duck, it is a duck." Statically typed languages such as Java require the common shape to be declared, as an **interface** or a shared superclass.

### Where it appears
- Different payment methods that all have `pay(amount)`.
- Different file formats that all have `save(document)`.
- Real and fake database objects with the same methods, so tests can run without a real database.

> Key idea: Long chains of `if` on a "type" value are a sign that polymorphism is missing.
#Q What decides which version of a method runs in a polymorphic call?
- The name of the variable
* The actual class of the object at run time
- The order the classes were defined
! This is dynamic dispatch.
#Q What is the main benefit of polymorphism over if/elif chains on a type?
- It uses less memory
* New kinds can be added without editing existing code
- It removes the need for classes
! Each new class brings its own behaviour.

#LESSON Abstraction and interfaces | 12
**Abstraction** means describing *what* something does while hiding *how*. You drive a car through a wheel and pedals without knowing how the engine works, and the same controls work on petrol and electric cars.

In code, an abstraction is usually an **interface**: a set of methods that a class promises to provide. An **abstract class** declares methods without implementing some of them, and cannot be instantiated itself.

```py
from abc import ABC, abstractmethod

class Storage(ABC):
    @abstractmethod
    def save(self, key, value): ...
    @abstractmethod
    def load(self, key): ...

class MemoryStorage(Storage):
    def __init__(self):
        self._data = {}
    def save(self, key, value):
        self._data[key] = value
    def load(self, key):
        return self._data.get(key)
```

Any code written against `Storage` works with `MemoryStorage`, a file-based version, or a database version, without change.

```diagram
        +-----------------+
        |  App logic      |   depends only on the interface
        +--------+--------+
                 |
        +--------v--------+
        |    Storage      |   (interface: save, load)
        +--------+--------+
        +--------+---------+----------------+
   MemoryStorage      FileStorage      DatabaseStorage
```

### Why this matters most of all
The app logic depends on a small, stable promise instead of a large, changeable implementation. You can swap storage, test with a fake, or let two people work on the two sides independently.

### The four pillars together
- **Encapsulation** hides state behind methods.
- **Abstraction** hides implementation behind an interface.
- **Inheritance** reuses and specialises.
- **Polymorphism** lets different implementations stand in for one another.

### A warning about OOP
Objects are a tool, not a goal. Wrapping simple functions in classes adds ceremony without benefit. Many good programs mix objects with plain functions and data.

> In industry: "Program to an interface, not an implementation" is among the most repeated pieces of design advice, because it is what makes large systems changeable.
#Q What does an interface define?
- How a class stores its data
* The methods a class promises to provide, without saying how
- The file a class is saved in
! An interface is a contract about behaviour.
#Q Why depend on an interface rather than a specific class?
- Interfaces run faster
* The implementation can be replaced or faked without changing the code that uses it
- It avoids writing any classes
! The dependency is on a small, stable promise.

#LESSON Arrays and linked lists | 14
A **data structure** is a way of arranging data in memory. The arrangement decides which operations are fast and which are slow, so choosing one is choosing your program's performance.

### Arrays
An **array** stores items side by side in one block of memory. Because every slot is the same size, the computer can compute where item `i` lives and jump straight to it.

```diagram
  index:   0     1     2     3
         +-----+-----+-----+-----+
         | 17  | 42  |  8  | 23  |      one continuous block
         +-----+-----+-----+-----+
```

- **Read or write by index:** one step, however long the array is.
- **Add at the end:** usually one step.
- **Insert or remove at the front or middle:** every later item must shift along. For a million items, that is up to a million moves.

Python's `list` and JavaScript's `Array` are **dynamic arrays**: when the block fills up, they allocate a bigger one (typically double) and copy everything across. That copy is expensive, but because it happens rarely, adding at the end is still cheap on average.

### Linked lists
A **linked list** stores each item in its own **node**, anywhere in memory. Each node holds a value and a reference to the next node.

```diagram
  head
   |
   v
 [17 | *]--> [42 | *]--> [8 | *]--> [23 | null]
```

- **Insert or remove at the front:** one step. Just change a reference.
- **Find the item at position i:** you must walk from the head, node by node.

```js
class Node {
  constructor(value) { this.value = value; this.next = null; }
}
```

### Choosing
| Operation | Array | Linked list |
|---|---|---|
| Get item by position | fast | slow |
| Add or remove at front | slow | fast |
| Add at end | fast | fast, if you keep a tail reference |
| Memory | compact | extra reference per item |

In practice arrays win most of the time, partly because items that sit together in memory are much faster for the processor to read (you will see why in Stage 4). Linked structures matter most as the building block of trees and graphs.
#Q Why is reading item 500 of an array fast?
- The array is sorted
* Its position can be computed directly because items are side by side and equal in size
- Arrays keep a list of where every item is
! The address is the start plus index times item size.
#Q Which operation is fast on a linked list but slow on an array?
- Reading the item at position i
* Inserting at the front
- Finding the length
! A linked list only changes one reference; an array must shift every item.

#LESSON Stacks and queues | 12
Two simple structures appear everywhere. Both restrict where you may add and remove, and that restriction is what makes them useful.

### Stack: last in, first out
A **stack** is a pile of plates. You add to the top (**push**) and remove from the top (**pop**). The last thing in is the first thing out (LIFO).

```diagram
   push 1, push 2, push 3        pop -> 3
        | 3 |  <- top
        | 2 |
        | 1 |
        +---+
```

```js
const stack = [];
stack.push(1); stack.push(2);
stack.pop();                    // 2
```

Where stacks appear:
- **Function calls.** Each call pushes a frame; returning pops it. This is "the call stack" in your error messages.
- **Undo.** Each action is pushed; undo pops the most recent.
- **Checking brackets.** Push each opener; on a closer, pop and check they match.
- **Going back** in a browser.

### Queue: first in, first out
A **queue** is a line at a shop. You join at the back (**enqueue**) and leave from the front (**dequeue**). First in, first out (FIFO).

```diagram
   front                         back
   +---+---+---+
   | 1 | 2 | 3 |   <- enqueue 4 joins here
   +---+---+---+
     ^ dequeue takes 1
```

Where queues appear: print jobs, requests waiting for a server, messages between programs, and exploring a map level by level (breadth-first search, coming soon).

### Implementing them well
A stack is simply an array used only at its end: both operations take one step.

A queue is harder. Removing from the front of an array shifts every item. Good queues use a linked list with head and tail references, or a **circular buffer**: an array with two indexes marking front and back that wrap around.

### Abstract data types
"Stack" and "queue" describe *behaviour*, not implementation. That makes each an **abstract data type**: you can use one knowing only its operations, and the implementation can change underneath.

> In industry: Message queues between services are queues in exactly this sense, scaled up. Understanding the small version makes the large one obvious.

#LESSON Hash tables | 14
How does a dictionary find a key among a million entries almost instantly? It does not search. It **computes** where the key should be.

A **hash table** is an array of slots (called **buckets**) plus a **hash function**. The hash function turns any key into a number; that number, reduced modulo the array length, is the slot index.

```diagram
   key "ada"  --hash-->  7392814  --mod 8-->  slot 6

   slots:  0    1    2    3    4    5    6        7
         [   ][   ][   ][   ][   ][   ]["ada":36][   ]
```

To look up `"ada"` later: hash it again, get slot 6, look there. One computation and one array access, regardless of how many entries exist.

A good hash function is **deterministic** (same key, same number, always), **fast**, and **spreads keys evenly**.

### Collisions
Two different keys can land in the same slot. This is a **collision**, and it is unavoidable. Two standard answers:

- **Chaining:** each slot holds a small list of the entries that hashed there.
- **Open addressing:** if the slot is taken, try the next one along.

If the table gets crowded, collisions pile up and lookups slow down. So when the table passes a certain fullness (the **load factor**), it allocates a bigger array and re-inserts everything. That is occasional heavy work that keeps the average operation fast.

### Costs
On average, insert, look up and delete each take a constant number of steps. In the worst case, with a terrible hash function, everything lands in one slot and it becomes a slow list.

### What you give up
A hash table has **no order**. You cannot ask it for "the smallest key" or "all keys between A and C" without looking at everything. Trees handle those questions.

### Sets
A **set** is a hash table that stores keys only. It answers "have I seen this before?" instantly.

```js
const seen = new Set();
seen.add("ada");
seen.has("ada");      // true
```

> Key idea: Replacing "search through a list" with "look up in a hash table or set" is the single most common way to make slow code fast.
#Q How does a hash table find the slot for a key?
- It searches every slot in order
* It computes a number from the key and uses it as an index
- It keeps the keys sorted
! The hash function maps the key to a position directly.
#Q What is a collision?
- Two keys with the same value
* Two different keys that hash to the same slot
- An error that stops the program
! Collisions are normal and are handled by chaining or probing.

#LESSON Trees | 14
A **tree** arranges data in a hierarchy: one **root** at the top, each **node** having zero or more **children**. A node without children is a **leaf**. Folders on a disk form a tree. So does the DOM of a web page.

### Binary search trees
In a **binary tree** each node has at most two children. A **binary search tree** (BST) adds a rule: everything in a node's left subtree is smaller than the node, and everything in its right subtree is larger.

```diagram
              50
            /    \
          30      70
         /  \    /  \
       20   40  60   80
```

To search for 60: start at 50. It is bigger, so go right to 70. It is smaller, so go left. Found, in three steps. Each step discards half of what remains, as long as the tree is balanced.

```js
function contains(node, target) {
  if (node === null) return false;
  if (target === node.value) return true;
  return target < node.value ? contains(node.left, target) : contains(node.right, target);
}
```

### Why trees matter
A BST keeps data **in order** while still allowing fast insert, delete and search. You can ask for the minimum, the maximum, or everything in a range, which a hash table cannot do.

### The catch: balance
Insert 10, 20, 30, 40 in that order and every node goes to the right. The "tree" is a linked list in disguise and search is slow again. **Self-balancing trees** (red-black trees, AVL trees, B-trees) rearrange themselves on insert to stay bushy. You rarely write one, but you use them constantly: database indexes are B-trees.

### Walking a tree
Visiting every node is a **traversal**.

- **In-order** (left, node, right) visits a BST in sorted order.
- **Pre-order** (node, left, right) is used to copy a tree.
- **Post-order** (left, right, node) is used to delete or evaluate one.
- **Level-order** visits top to bottom, row by row, using a queue.

The **height** of a tree is the number of steps from the root to the deepest leaf. A balanced tree of a million nodes has a height of only about 20.
#Q In a binary search tree, where are values smaller than a node stored?
* In its left subtree
- In its right subtree
- In its parent
! Smaller to the left, larger to the right, at every node.
#Q What happens if you insert already-sorted values into a plain binary search tree?
- It becomes perfectly balanced
* It degenerates into a chain, and searching becomes slow
- The insertions fail
! Every new value goes the same way, producing a list-like tree.

#LESSON Graphs | 12
A **graph** is a set of **vertices** (also called nodes) joined by **edges**. It is the most general structure: lists and trees are special kinds of graph.

Graphs model anything made of things and connections: cities and roads, people and friendships, web pages and links, tasks and the tasks they depend on.

```diagram
      A ------- B
      |       / |
      |     /   |
      C ---     D
```

### Vocabulary
- **Directed** edges go one way (A follows B). **Undirected** edges go both ways (A and B are friends).
- **Weighted** edges carry a number: a distance, a cost, a time.
- A **path** is a sequence of edges from one vertex to another. A **cycle** is a path that returns to its start.
- A graph is **connected** if there is a path between every pair of vertices.

### Storing a graph
The usual choice is an **adjacency list**: for each vertex, the list of its neighbours.

```js
const graph = {
  A: ["B", "C"],
  B: ["A", "C", "D"],
  C: ["A", "B"],
  D: ["B"],
};
```

The alternative, an **adjacency matrix**, is a grid with a mark wherever two vertices are joined. It answers "are A and D connected?" in one step but uses space for every possible pair, which is wasteful when most pairs are not connected.

### Exploring a graph
Two fundamental methods, studied in depth in Stage 3:

- **Breadth-first search** (BFS) explores in rings: all neighbours first, then their neighbours. It uses a queue and finds the path with the fewest edges.
- **Depth-first search** (DFS) follows one path as far as it goes, then backs up. It uses a stack, or recursion.

Both must remember which vertices they have **visited**, or a cycle would trap them forever. A set is the right tool for that.

> In industry: Route planning, recommendation systems, dependency resolution in package managers and the analysis of networks are all graph problems. Recognising "this is a graph" is half the work.
#Q What makes a graph different from a tree?
- A graph has no nodes
* A graph may contain cycles and need not have a root
- A graph cannot be stored in a program
! A tree is a connected graph without cycles.
#Q Why must a graph search keep a record of visited vertices?
- To sort the vertices
* To avoid going round a cycle forever
- To save memory
! Without it, cycles cause endless revisiting.

    const node = { value: x, next: null };
    if (this.head === null) this.head = node;
    else { let n = this.head; while (n.next !== null) n = n.next; n.next = node; }

#LESSON Measuring efficiency: Big O | 15
Two programs can both be correct while one finishes instantly and the other takes a year. To compare them we need a measure that does not depend on the computer or the language. That measure is how the **number of steps grows as the input grows**.

We call the input size **n**. Consider searching an unsorted list for a value: in the worst case you look at all n items. Double the list and the work doubles. We say this is **O(n)**, read "order n" or "linear time".

**Big O notation** describes growth while ignoring details that do not matter at scale:

- **Drop constants.** 2n steps and 50n steps are both O(n). They grow the same way.
- **Keep only the fastest-growing term.** n² + 100n + 5 is O(n²), because for large n the n² dwarfs the rest.

### The common growth rates

| Big O | Name | Steps when n = 1,000,000 | Example |
|---|---|---|---|
| O(1) | constant | 1 | array index, hash lookup |
| O(log n) | logarithmic | about 20 | binary search |
| O(n) | linear | 1,000,000 | one loop over the data |
| O(n log n) | linearithmic | about 20,000,000 | good sorting |
| O(n²) | quadratic | 1,000,000,000,000 | a loop inside a loop |
| O(2ⁿ) | exponential | more than atoms in the universe | trying every subset |

### Reading it from code
- A single statement: O(1).
- One loop over n items: O(n).
- A loop inside a loop, both over n: O(n²).
- A loop that halves the remaining work each time: O(log n).
- Steps one after another: add them, then keep the largest.

```js
for (const a of items) {          // n times
  for (const b of items) {        //   n times each
    if (a + b === target) return true;
  }
}                                 // O(n²)
```

### Worst case, and space
Unless stated otherwise, Big O means the **worst case**. The same notation measures memory: **space complexity** is how much extra memory an algorithm needs as n grows.

> Key idea: Big O is not about how fast something is on small input. It is about what happens when the input gets large.

> In industry: "This is quadratic; it will fall over when the customer list grows" is a routine review comment. Engineers are expected to see it by reading the loops.
#Q What is the time complexity of a loop over n items nested inside another loop over n items?

- O(2n)
* O(n²)
! The inner loop runs n times for each of the n outer passes.
#Q An algorithm takes 3n² + 20n + 7 steps. What is its Big O?
- O(3n²)
* O(n²)
- O(n² + n)
! Drop constants and lower-order terms.

#LESSON Searching | 12
### Linear search
To find a value in an unsorted list there is no trick: check each item in turn. That is **linear search**, O(n).

```js
function linearSearch(items, target) {
  for (let i = 0; i < items.length; i++) {
    if (items[i] === target) return i;
  }
  return -1;
}
```

### Binary search
If the list is **sorted**, you can do far better. Look at the middle item. If it is your target, done. If your target is smaller, it can only be in the left half; if larger, only in the right half. Throw the other half away and repeat.

```diagram
   find 23 in  [ 3, 8, 15, 21, 23, 42, 57 ]
                          ^ middle is 21: 23 is larger, keep the right half
                               [ 23, 42, 57 ]
                                     ^ middle is 42: 23 is smaller, keep the left half
                               [ 23 ]   found
```

Each step halves what is left, so a million items take about 20 steps: **O(log n)**.

```js
function binarySearch(items, target) {
  let lo = 0, hi = items.length - 1;
  while (lo <= hi) {
    const mid = Math.floor((lo + hi) / 2);
    if (items[mid] === target) return mid;
    if (items[mid] < target) lo = mid + 1;
    else hi = mid - 1;
  }
  return -1;
}
```

### Getting it right
Binary search is famous for being easy to describe and easy to get wrong. The reliable way to write it is to hold an **invariant**: "if the target is present, it is between `lo` and `hi` inclusive". Check that every line keeps that true.

- `lo <= hi`, not `<`: a range of one item must still be examined.
- `mid + 1` and `mid - 1`: `mid` has been checked, so exclude it. Using `mid` alone can loop forever.

### What log n means
log₂ n is the number of times you can halve n before reaching 1. It grows extremely slowly: log₂ of a billion is about 30.

### The trade-off
Binary search needs sorted data, and sorting costs O(n log n). If you search once, linear search is fine. If you search many times, sort once and binary-search each time, or use a hash table.

#LESSON Sorting: the simple algorithms | 12
Sorting is worth studying closely. It is useful in its own right, and it is the clearest place to see how different ideas lead to very different speeds.

### Selection sort
Find the smallest item and swap it into position 0. Find the smallest of the rest and swap it into position 1. Continue.

```js
function selectionSort(a) {
  for (let i = 0; i < a.length - 1; i++) {
    let min = i;
    for (let j = i + 1; j < a.length; j++) if (a[j] < a[min]) min = j;
    [a[i], a[min]] = [a[min], a[i]];
  }
  return a;
}
```

It always makes about n²/2 comparisons: **O(n²)**.

### Insertion sort
Keep the left part sorted. Take the next item and slide it left into its correct place, the way you sort playing cards in your hand.

```diagram
  [ 5 | 2  9  1 ]      take 2, slide it before 5
  [ 2  5 | 9  1 ]      take 9, already in place
  [ 2  5  9 | 1 ]      take 1, slide it to the front
  [ 1  2  5  9 ]
```

It is **O(n²)** in the worst case, but if the data is already nearly sorted each item barely moves and it runs in close to **O(n)**. That makes it the best choice for small or nearly sorted arrays, and real sorting libraries use it for exactly that.

### Bubble sort
Repeatedly sweep through, swapping neighbours that are out of order. Simple to explain, O(n²), and slower in practice than insertion sort. It is taught mainly as a first example.

### Two properties to know
- A sort is **stable** if items that compare equal keep their original order. This matters when sorting records by one field after another. Insertion sort is stable; selection sort is not.
- A sort is **in place** if it needs only a constant amount of extra memory.

### Why O(n²) is not good enough
Sorting a million items with an O(n²) algorithm takes on the order of a trillion steps: hours. The next lesson's algorithms do it in a fraction of a second.

* Insertion sort

#Q What does it mean for a sort to be stable?
- It never crashes
* Items that compare equal keep their original relative order
- It uses no extra memory
! Stability matters when sorting by several fields in turn.

#LESSON Recursion | 14
A **recursive** function is one that calls itself. It solves a problem by reducing it to a smaller version of the same problem.

Every correct recursion has two parts:

1. A **base case**: an input small enough to answer directly, with no further call.
2. A **recursive case**: reduce the problem toward the base case, and call yourself on the smaller problem.

```js
function factorial(n) {
  if (n <= 1) return 1;              // base case
  return n * factorial(n - 1);       // recursive case
}
```

### How it runs
Each call waits for the call it made. The waiting calls pile up on the **call stack**, then finish in reverse order.

```diagram
  factorial(4)
    4 * factorial(3)
          3 * factorial(2)
                2 * factorial(1)
                      returns 1
                returns 2
          returns 6
    returns 24
```

Forget the base case, or fail to move toward it, and the calls never stop. The stack fills and the program dies with "maximum call stack size exceeded", a **stack overflow**.

### How to think recursively
Do not try to follow every call in your head. Instead, **trust the function**: assume it already works for any smaller input, and ask only "how do I use the answer to the smaller problem to answer this one?".

Sum of a list: the first item plus the sum of the rest. The sum of an empty list is 0.

```js
const sum = (items) => (items.length === 0 ? 0 : items[0] + sum(items.slice(1)));
```

### Where recursion fits naturally
Structures that are themselves recursive: a tree is a node whose children are trees; a folder contains folders. Walking them recursively is far simpler than with loops.

### A warning
Naive recursion can repeat work enormously.

```js
const fib = (n) => (n < 2 ? n : fib(n - 1) + fib(n - 2));
```

`fib(40)` makes hundreds of millions of calls because it recomputes the same values over and over. It is **O(2ⁿ)**. Remembering answers already computed (**memoization**) fixes it, and leads to dynamic programming in Stage 3.

> Key idea: Base case, smaller problem, trust the function.

#LESSON Divide and conquer: merge sort and quicksort | 15
**Divide and conquer** is a recipe for fast algorithms: split the problem into smaller parts, solve each part (usually recursively), then combine the answers.

### Merge sort
1. Split the array in half.
2. Sort each half (recursively).
3. **Merge** the two sorted halves into one.

Merging is the clever part and it is easy: look at the front of both halves, take the smaller, repeat.

```diagram
        [ 7  2  9  4 ]
        /            \
    [ 7  2 ]       [ 9  4 ]          split
    /     \        /     \
  [7]    [2]     [9]    [4]          single items are already sorted
    \     /        \     /
    [ 2  7 ]       [ 4  9 ]          merge
        \            /
        [ 2  4  7  9 ]               merge
```

```js
function mergeSort(a) {
  if (a.length <= 1) return a;
  const mid = Math.floor(a.length / 2);
  const left = mergeSort(a.slice(0, mid)), right = mergeSort(a.slice(mid));
  const out = []; let i = 0, j = 0;
  while (i < left.length && j < right.length) out.push(left[i] <= right[j] ? left[i++] : right[j++]);
  return out.concat(left.slice(i), right.slice(j));
}
```

**Why it is fast.** Halving n repeatedly gives log n levels. Each level merges n items in total. So the work is **O(n log n)**, always. It is stable, but needs O(n) extra memory.

### Quicksort
1. Pick an item, the **pivot**.
2. **Partition**: move everything smaller than the pivot to its left and everything larger to its right.
3. Sort the two sides recursively.

Quicksort sorts in place and is very fast in practice, averaging **O(n log n)**. Its weakness is a bad pivot: if the pivot is always the smallest item, one side is empty and it degrades to **O(n²)**. Choosing the pivot at random makes that vanishingly unlikely.

### A hard limit
Any sort that works only by comparing items needs at least on the order of n log n comparisons in the worst case. This is a proven lower bound, so merge sort is essentially as good as comparison sorting can be.

### What your language uses
`sort()` in Python and in modern JavaScript engines uses **Timsort**, a hybrid of merge sort and insertion sort tuned for real data. In practice you call the built-in sort. You study these algorithms to learn to analyse and design your own.
#Q What is the time complexity of merge sort?
- O(n)
* O(n log n)
- O(n²)
! There are log n levels and each level does n work.
#Q What makes quicksort slow in the worst case?
- Sorting very small arrays
* Consistently choosing a pivot that splits the array very unevenly
- Using recursion
! Uneven splits give n levels instead of log n.

#LESSON Static and dynamic typing | 12
In Python and JavaScript a variable can hold anything, and type mistakes show up only when the faulty line runs. These are **dynamically typed** languages. In Java, C, C++, C#, Go, Rust and TypeScript, every variable has a declared type and a **compiler** checks the whole program before it runs. These are **statically typed**.

```py
def area(w, h):
    return w * h

area("3", 4)        # Python happily returns "3333"
```

```ts
function area(w: number, h: number): number {
  return w * h;
}

area("3", 4);       // compile error: a string is not a number
```

### What the checker buys you
- **Errors found early**, before any user meets them, in every branch, not only the ones you tested.
- **Documentation that cannot go out of date.** The signature says what goes in and what comes out.
- **Tools.** Editors can autocomplete, jump to definitions and rename safely because they know every type.
- **Safer change.** Alter a function's parameters and the compiler lists every call that must be updated.

### What it costs
More to write, a compile step, and occasionally fighting the type checker to express something it cannot follow.

### Compiled and interpreted
A **compiler** translates source code into another form ahead of time (machine code for C and Rust; bytecode for Java). An **interpreter** reads and runs the source directly. Static typing and compilation often go together but are separate ideas: Python can be type-checked with an external tool, and JavaScript is compiled as it runs.

### Strong and weak
A separate question is how strict a language is about mixing types. Python refuses `"3" + 4`. JavaScript converts and gives `"34"`. Python is called **strongly typed** and JavaScript **weakly typed**, though both are dynamic.

> Key idea: Static typing moves a whole class of bugs from "found by a user at run time" to "found by the compiler before release".

> In industry: Most large teams choose static typing because its benefits grow with the size of the codebase and the number of people working on it.
#Q When does a statically typed language detect that a string was passed where a number is required?
* When the program is compiled, before it runs
- Only when that line executes
- Never
! The compiler checks types across the whole program in advance.
#Q Which is a benefit of static types?
- Programs need no testing
* Editors and compilers can find mistakes and support safe renaming
- Code is always shorter
! Type information powers both checking and tooling.

#LESSON TypeScript | 14
**TypeScript** is JavaScript with types. Every JavaScript program is already a TypeScript program; you add **type annotations**, and a compiler checks them and then outputs plain JavaScript.

```ts
let count: number = 0;
const names: string[] = ["Ada", "Alan"];

function greet(name: string, shout: boolean = false): string {
  return shout ? name.toUpperCase() : name;
}
```

You annotate less than you might expect, because TypeScript **infers** types: `let count = 0` is already known to be a number.

### Describing object shapes

```ts
interface User {
  id: number;
  name: string;
  email?: string;          // optional
}

function label(u: User): string {
  return `${u.id}: ${u.name}`;
}
```

TypeScript uses **structural typing**: any object with the right properties counts as a `User`, whatever it is called.

### Union types and narrowing
A value can be one of several types. The compiler makes you handle each case.

```ts
function size(x: string | string[]): number {
  if (typeof x === "string") return x.length;   // here x is a string
  return x.length;                              // here x is a string[]
}
```

### null safety
With strict settings, a value that might be `null` or `undefined` cannot be used until you check. This eliminates the most common runtime error in JavaScript, "cannot read properties of undefined".

```ts
function first(xs: number[]): number | undefined { return xs[0]; }

const f = first([]);
if (f !== undefined) console.log(f + 1);
```

### Generics
A **generic** function works for any type while keeping that type known:

```ts
function last<T>(items: T[]): T | undefined {
  return items[items.length - 1];
}
const n = last([1, 2, 3]);      // n is number | undefined
```

### Types vanish at run time
Types are checked and then removed. They do not validate data arriving from outside your program (a network response, user input). That still needs run-time checks.

> In industry: TypeScript is now the default for professional web front ends and much server-side JavaScript.

#LESSON Java | 14
**Java** is a statically typed, object-oriented language that runs on the Java Virtual Machine (JVM). It powers a great deal of enterprise software and Android. Everything you learned about classes applies; the syntax is stricter and more explicit.

```java
public class Main {
    public static void main(String[] args) {
        int total = 0;
        for (int i = 1; i <= 5; i++) {
            total += i;
        }
        System.out.println("Total: " + total);
    }
}
```

What to notice:

- All code lives inside a **class**. The program starts at `main`.
- Every variable has a declared type: `int`, `double`, `boolean`, `String`.
- Statements end with semicolons; blocks use curly brackets.

### Classes in Java

```java
public class Account {
    private double balance;                 // truly private

    public Account(double opening) {        // constructor
        this.balance = opening;
    }

    public void deposit(double amount) {
        if (amount <= 0) throw new IllegalArgumentException("amount must be positive");
        balance += amount;
    }

    public double getBalance() { return balance; }
}
```

`private` is enforced by the compiler: no code outside the class can touch `balance`. `this` plays the role of Python's `self`.

### Interfaces

```java
interface Shape { double area(); }

class Circle implements Shape {
    private final double r;
    Circle(double r) { this.r = r; }
    public double area() { return Math.PI * r * r; }
}
```

A class that says `implements Shape` must provide `area()`, or it will not compile. This is the declared polymorphism mentioned in the OOP course.

### Collections

```java
List<String> names = new ArrayList<>();
names.add("Ada");
Map<String, Integer> ages = new HashMap<>();
ages.put("Ada", 36);
```

`List<String>` uses **generics**: a list that holds only strings, checked by the compiler.

### Compile, then run
`javac Main.java` compiles to **bytecode**, and `java Main` runs it on the JVM. The JVM manages memory for you with a **garbage collector**, which finds objects nothing refers to and reclaims them.

> In industry: Java's strictness and long-term stability make it a common choice for large systems maintained for decades. C# is closely related in design and feel.

#LESSON C: memory and pointers | 16
**C** is small, fast and close to the machine. Operating systems, databases and the interpreters of other languages are written in it. Learning C teaches you what the higher-level languages do for you.

```c
#include <stdio.h>

int main(void) {
    int total = 0;
    for (int i = 1; i <= 5; i++) {
        total += i;
    }
    printf("Total: %d\n", total);
    return 0;
}
```

`#include` pulls in declarations for library functions. `printf` prints using a format string: `%d` is replaced by an integer.

### Memory is a row of numbered boxes
Every variable lives at an **address**. A **pointer** is a variable that holds an address.

```c
int x = 42;
int *p = &x;        // & means "address of": p points to x
printf("%d\n", *p); // * means "the value at": prints 42
*p = 7;             // changes x through the pointer
```

```diagram
   address:   1000          1004
            +-------+     +-------+
        x:  |  42   |  p: | 1000  |   p holds the address of x
            +-------+     +-------+
```

### Why pointers exist
C passes arguments **by value**: a function receives copies. To let a function change the caller's variable, pass its address.

```c
void swap(int *a, int *b) {
    int t = *a; *a = *b; *b = t;
}
swap(&x, &y);
```

### Arrays and strings
An array is a block of consecutive boxes, and its name behaves like a pointer to the first one. C does **not** check that an index is within the array. A string is an array of characters ending with a zero byte.

### Stack and heap
- Local variables live on the **stack** and disappear when the function returns.
- Memory you need to outlive a function is requested from the **heap** with `malloc` and must be returned with `free`.

```c
int *nums = malloc(10 * sizeof(int));
/* use nums[0] to nums[9] */
free(nums);
```

### The dangers
There is no garbage collector and no safety net:

- Forget `free`: a **memory leak**.
- Use memory after `free`, or return the address of a local variable: a **dangling pointer**.
- Write past the end of an array: a **buffer overflow**, the cause of a large share of historical security vulnerabilities.

> Key idea: In C, you manage memory. In Python, Java and JavaScript, the language does. Knowing what is being managed makes you better at all of them.
#Q What does a pointer hold?
- A copy of a value
* The memory address of a value
- The type of a value
! Dereferencing the pointer with `*` reaches the value at that address.
#Q What is a memory leak?
- Writing past the end of an array
* Heap memory that is allocated but never freed
- A variable with no type
! The program keeps holding memory it no longer uses.

#LESSON C++ | 12
**C++** began as "C with classes" and grew into a large language that offers both low-level control and high-level abstractions. Game engines, browsers, trading systems and much scientific software are written in it.

```cpp
#include <iostream>
#include <vector>
#include <string>

int main() {
    std::vector<int> nums = {4, 9, 2};
    int total = 0;
    for (int n : nums) total += n;
    std::cout << "Total: " << total << std::endl;
    return 0;
}
```

`std::vector` is a dynamic array, `std::string` is a real string type, and `std::cout <<` prints. These come from the **standard library**, which removes most of the reasons to use raw C arrays and `malloc`.

### Classes with constructors and destructors

```cpp
class Buffer {
public:
    Buffer(int n) : data(new int[n]), size(n) {}   // constructor acquires
    ~Buffer() { delete[] data; }                   // destructor releases
private:
    int *data;
    int size;
};
```

A **destructor** runs automatically when an object goes out of scope. This enables the central idea of modern C++:

### RAII
**Resource Acquisition Is Initialization**: tie every resource (memory, a file, a lock) to an object. Acquire it in the constructor, release it in the destructor. Because destructors always run when scope ends, even on an error, the resource cannot leak.

**Smart pointers** apply this to heap memory:

```cpp
auto p = std::make_unique<Account>(100);   // freed automatically when p goes out of scope
```

`unique_ptr` has exactly one owner. `shared_ptr` counts owners and frees when the count reaches zero. Modern C++ code rarely writes `new` or `delete` directly.

### References
A **reference** is another name for an existing variable. It behaves like a pointer that cannot be null and needs no `*`.

```cpp
void addOne(int &n) { n += 1; }
```

### Templates
Templates are C++ generics: `std::vector<int>`, `std::vector<std::string>`. The compiler generates specialised code for each type, giving abstraction with no run-time cost.

> Key idea: C++ aims for "zero-cost abstractions": you do not pay at run time for features you use well. The price is a complex language that demands discipline.

> In industry: C++ is chosen when performance and control over memory matter most. Rust, in Stage 4, pursues the same goals with the compiler enforcing memory safety.
#Q What does RAII guarantee?
- That programs never have bugs
* That a resource is released when the object that owns it goes out of scope
- That all variables are public
! The destructor runs automatically, even when an error occurs.
#Q What is the advantage of std::unique_ptr over a raw pointer with new and delete?
- It is faster to type
* The memory is freed automatically, so it cannot be leaked or freed twice by mistake
- It can point to several objects at once
! Ownership is expressed in the type and enforced.

#LESSON Advanced Python and JavaScript | 14
Both languages have features that make code shorter and clearer once you know them. All are built on ideas you already have.

### Python: comprehensions
A **list comprehension** builds a list in one expression.

```py
squares = [n * n for n in range(5)]                 # [0, 1, 4, 9, 16]
evens = [n for n in range(10) if n % 2 == 0]
lengths = {word: len(word) for word in ["a", "bb"]} # dictionary comprehension
```

Read it as "n squared, for each n in the range".

### Python: unpacking, enumerate and zip

```py
x, y = 3, 4
for i, name in enumerate(["Ada", "Alan"]):
    print(i, name)
for name, age in zip(names, ages):
    print(name, age)
```

### Python: functions as values
Functions can be passed like any other value. `sorted` takes a `key` function:

```py
people.sort(key=lambda p: p["age"])
```

A `lambda` is a small unnamed function.

### Python: generators
A function containing `yield` produces values one at a time, on demand, without building the whole list in memory.

```py
def countdown(n):
    while n > 0:
        yield n
        n -= 1
```

### JavaScript: closures
A function remembers the variables that existed where it was created. That is a **closure**.

```js
function makeCounter() {
  let count = 0;
  return () => { count += 1; return count; };
}
const next = makeCounter();
next(); next();      // 1, then 2
```

`count` is private to the returned function: nothing else can reach it. Closures are how JavaScript gets private state without classes, and why event listeners can see the variables around them.

### JavaScript: destructuring and spread

```js
const { name, age } = user;
const [first, ...rest] = [1, 2, 3];
const copy = { ...user, age: 37 };       // a new object with one change
```

### JavaScript: higher-order functions
A function that takes or returns a function is **higher-order**. `map`, `filter` and `reduce` are examples, and you can write your own:

```js
const twice = (f) => (x) => f(f(x));
twice((n) => n + 3)(10);     // 16
```

### Both: exceptions
`try` / `except` in Python and `try` / `catch` in JavaScript handle errors; `raise` and `throw` signal them. Catch only the errors you can deal with, and never silently swallow one.

> In industry: Idiomatic code, written the way the language's community expects, is easier for colleagues to read. Learning these features is part of becoming fluent, not showing off.
