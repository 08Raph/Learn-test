#LESSON Logic and methods of proof | 15
Computer science at this level rests on **proof**: an argument that establishes a statement beyond doubt, for every case, not just the ones you tested. A test shows a program works on some inputs. A proof shows it works on all of them.

### Propositions and connectives
A **proposition** is a statement that is true or false. Connectives build larger ones.

| Symbol | Name | True when |
|---|---|---|
| not P | negation | P is false |
| P and Q | conjunction | both are true |
| P or Q | disjunction | at least one is true |
| P → Q | implication | P is false, or Q is true |
| P ↔ Q | biconditional | both have the same truth value |

Implication surprises people: P → Q is false **only** when P is true and Q is false. "If it rains, I carry an umbrella" is not broken by a dry day.

Useful equivalences:

- **De Morgan:** not (P and Q) is (not P) or (not Q); not (P or Q) is (not P) and (not Q).
- **Contrapositive:** P → Q is equivalent to (not Q) → (not P).
- The **converse** Q → P is *not* equivalent to P → Q.

### Quantifiers
- **For all** (∀): the statement holds for every element.
- **There exists** (∃): it holds for at least one.

Negation swaps them: "not every x has property P" means "some x lacks P". To disprove a universal claim, one **counterexample** is enough. To prove one, examples are never enough.

Order matters. "For every person there exists a parent" is true. "There exists a parent for every person" (one parent of everybody) is false.

### Direct proof
Assume the hypothesis and reason to the conclusion.

**Claim.** The sum of two even integers is even.
**Proof.** Let a and b be even. Then a = 2m and b = 2n for some integers m, n. So a + b = 2m + 2n = 2(m + n), which is twice an integer, hence even. ∎

### Proof by contrapositive
To prove P → Q, prove (not Q) → (not P).

**Claim.** If n² is even, then n is even.
**Proof.** We prove the contrapositive: if n is odd, n² is odd. Let n = 2k + 1. Then n² = 4k² + 4k + 1 = 2(2k² + 2k) + 1, which is odd. ∎

### Proof by contradiction
Assume the claim is false and derive an impossibility.

**Claim.** √2 is irrational.
**Proof.** Suppose √2 = a/b with a, b integers sharing no common factor. Then a² = 2b², so a² is even, so a is even (by the previous claim): a = 2c. Then 4c² = 2b², so b² = 2c², so b is even. Both a and b are even, contradicting that they share no factor. ∎

### Other techniques
- **Proof by cases:** split into exhaustive cases and prove each.
- **Existence proofs:** exhibit an example (constructive), or show one must exist.
- **Uniqueness:** assume two and show they are equal.

### Writing proofs
State what is to be proved. Name your method. Justify each step. Define every symbol. End clearly. A proof is written for a sceptical reader.

> Key idea: Evidence from examples suggests; only a proof establishes. A single counterexample refutes.

#LESSON Sets, relations and functions | 14
### Sets
A **set** is an unordered collection of distinct elements. x ∈ A means x is an element of A.

- **Subset:** A ⊆ B if every element of A is in B.
- **Union** A ∪ B: elements in either. **Intersection** A ∩ B: elements in both. **Difference** A \ B: in A and not in B.
- **Cartesian product** A × B: all ordered pairs (a, b).
- **Power set** P(A): the set of all subsets of A. If A has n elements, P(A) has 2ⁿ.

To prove two sets equal, prove each is a subset of the other.

### Relations
A **relation** on a set A is a set of ordered pairs from A × A. A database table is a relation; so is "follows" on a social network.

Properties a relation R may have:

- **Reflexive:** every a is related to itself.
- **Symmetric:** if a R b then b R a.
- **Antisymmetric:** if a R b and b R a then a = b.
- **Transitive:** if a R b and b R c then a R c.

An **equivalence relation** is reflexive, symmetric and transitive. It splits the set into disjoint **equivalence classes**. "Has the same remainder when divided by 5" is one, with five classes. Every hash table relies on this: keys are grouped into classes by hash value.

A **partial order** is reflexive, antisymmetric and transitive: "is a subset of", "divides", "must be built before". Some pairs may be incomparable. A **total order** compares every pair. A topological sort turns a partial order into a compatible total one.

### Functions
A **function** f: A → B assigns to each element of A exactly one element of B.

- **Injective** (one-to-one): different inputs give different outputs.
- **Surjective** (onto): every element of B is an output.
- **Bijective:** both. A bijection has an inverse and pairs the elements of A and B exactly.

```diagram
   injective, not surjective       surjective, not injective        bijective
     1 --> a                         1 --> a                          1 --> a
     2 --> b                         2 --> a                          2 --> b
           c                         3 --> b                          3 --> c
```

Bijections define size: two sets have the same **cardinality** exactly when a bijection exists between them.

### The pigeonhole principle
If n + 1 objects are placed in n boxes, some box holds at least two. Equivalently, no function from a larger finite set to a smaller one is injective.

Consequences: any hash function from a large key space to a smaller table **must** have collisions. Lossless compression cannot shrink every file, since there are more files of length n than shorter files.

### Infinite sets
The natural numbers, the integers and the rationals can all be put in a list: they are **countable**. Cantor's **diagonal argument** shows the real numbers cannot.

**Proof sketch.** Suppose all infinite binary sequences were listed as s₁, s₂, s₃, ... Build a sequence d whose n-th digit is the opposite of the n-th digit of sₙ. Then d differs from every sₙ in position n, so d is not in the list. Contradiction. ∎

The same argument shows there are more functions than programs (programs are finite strings, hence countable). So **some functions cannot be computed by any program**. You will meet a specific one in Theory of Computation.

> Key idea: Relations and functions are the vocabulary in which databases, type systems and algorithms are defined. Their properties decide what operations are safe.

#LESSON Induction and recursion | 15
**Mathematical induction** proves a statement for all natural numbers. It is the proof technique of computer science, because it mirrors recursion and loops exactly.

### The principle
To prove P(n) for all n ≥ 0:

1. **Base case:** prove P(0).
2. **Inductive step:** assume P(k) holds (the **inductive hypothesis**) and prove P(k + 1).

Like dominoes: the first falls, and each knocks over the next.

### Example
**Claim.** 1 + 2 + ... + n = n(n + 1)/2 for all n ≥ 1.

**Proof.** *Base:* for n = 1, the left side is 1 and the right side is 1·2/2 = 1. *Step:* assume 1 + ... + k = k(k + 1)/2. Then

```text
1 + ... + k + (k + 1) = k(k + 1)/2 + (k + 1)
                      = (k + 1)(k/2 + 1)
                      = (k + 1)(k + 2)/2
```

which is the formula for n = k + 1. ∎

### Strong induction
In the step you may assume P holds for **all** values up to k, not just k. Use it when a case depends on several smaller ones.

**Claim.** Every integer n ≥ 2 is a product of primes.
**Proof.** Assume the claim for all integers from 2 to k. If k + 1 is prime, it is a product of one prime. Otherwise k + 1 = a·b with 2 ≤ a, b ≤ k. By hypothesis a and b are products of primes, so k + 1 is too. ∎

### Structural induction
Induction works on any recursively defined structure: lists, trees, expressions. Prove the property for the base structures, and prove that each way of building a larger structure preserves it.

**Claim.** A binary tree in which every internal node has exactly two children has one more leaf than internal nodes.
**Proof.** *Base:* a single leaf has 1 leaf and 0 internal nodes. *Step:* a tree with root and subtrees L and R. By hypothesis leaves(L) = internal(L) + 1 and leaves(R) = internal(R) + 1. The whole tree has leaves(L) + leaves(R) = internal(L) + internal(R) + 2 leaves and internal(L) + internal(R) + 1 internal nodes. The difference is 1. ∎

### Proving programs correct
A recursive function is proved correct by induction on its input: the base case is correct, and if the recursive calls are correct then so is the whole.

A loop is proved correct with a **loop invariant**: a statement that is

1. true before the loop starts (**initialisation**),
2. kept true by each iteration (**maintenance**), and
3. gives the desired result when the loop ends (**termination**).

```python
def total(xs):
    s = 0
    i = 0
    # invariant: s is the sum of xs[0..i-1]
    while i < len(xs):
        s = s + xs[i]
        i = i + 1
    return s
```

Initially i = 0 and s = 0, the sum of no elements. Each pass adds xs[i] and advances i, preserving the invariant. At exit i = len(xs), so s is the sum of everything. That is induction on the number of iterations.

To prove **termination**, find a quantity that is a non-negative integer and strictly decreases each iteration (here, len(xs) − i).

### Recurrences
The running time of a recursive algorithm satisfies a **recurrence**. Merge sort: T(n) = 2T(n/2) + n, which solves to O(n log n). Solutions are guessed and then verified by induction, or read from the **master theorem**.

> Key idea: Recursion defines; induction proves. Whenever you write a loop or a recursive function, an inductive argument explains why it works.

#LESSON Counting and combinatorics | 14
Counting tells you how large a search space is, how likely an event is, and whether an algorithm is feasible.

### Two basic rules
- **Product rule:** if a task has a steps with m and n choices, there are m × n outcomes. An 8-character password over 62 symbols has 62⁸ ≈ 2.2 × 10¹⁴ possibilities.
- **Sum rule:** if a task can be done in one of m ways **or** one of n ways, with no overlap, there are m + n ways.

### Permutations
An ordered arrangement. n distinct objects can be ordered in **n!** ways. Choosing and ordering k of n:

```text
P(n, k) = n! / (n − k)!
```

n! grows faster than any exponential: 20! is about 2.4 × 10¹⁸. An algorithm that tries every ordering is hopeless beyond tiny inputs.

### Combinations
An unordered selection of k from n:

```text
C(n, k) = n! / (k! (n − k)!)
```

read "n choose k". Each combination corresponds to k! permutations, which is why we divide.

Facts: C(n, k) = C(n, n − k). C(n, 0) = 1.

**Pascal's rule:** C(n, k) = C(n − 1, k − 1) + C(n − 1, k).
**Proof (combinatorial).** Fix one element x. A k-subset either contains x, and the remaining k − 1 are chosen from the other n − 1, or it does not, and all k come from the other n − 1. ∎

Proving an identity by counting the same set in two ways is called **double counting**.

### The binomial theorem
```text
(x + y)ⁿ = sum over k of C(n, k) xᵏ yⁿ⁻ᵏ
```

Setting x = y = 1 gives: the numbers C(n, 0) + C(n, 1) + ... + C(n, n) add up to 2ⁿ, the number of subsets.

### Inclusion-exclusion
For overlapping sets:

```text
size(A ∪ B) = size(A) + size(B) − size(A ∩ B)
```

With three sets, add the singles, subtract the pairs, add back the triple. How many integers from 1 to 100 are divisible by 2 or 3? 50 + 33 − 16 = 67.

### Stars and bars
The number of ways to distribute n identical items into k distinct boxes is C(n + k − 1, k − 1). Picture n stars and k − 1 bars in a row.

### Counting in computing
- **Decision trees:** a comparison sort must distinguish n! orderings. A binary tree with n! leaves has height at least log₂(n!), which is about n log n. So **no comparison sort can beat O(n log n)** in the worst case. A counting argument proves a lower bound on every possible algorithm.
- **Birthday paradox:** among 23 people, two probably share a birthday. In general, collisions become likely after about √N random draws from N values. A 64-bit hash sees collisions after roughly 2³² items, which is why security needs larger outputs.
- **Key spaces:** a 128-bit key has 2¹²⁸ ≈ 3.4 × 10³⁸ values, beyond any brute-force search.

### Recurrences count too
The number of binary strings of length n with no two adjacent 1s satisfies a(n) = a(n − 1) + a(n − 2): the Fibonacci recurrence. Setting up a recurrence is often the easiest way to count, and it translates directly into dynamic programming.

> Key idea: Before designing an algorithm, count what it has to search. The count tells you whether brute force is possible and what a lower bound might be.

#LESSON Graph theory | 14
You have used graphs as a data structure. Graph **theory** proves what must be true of them, and those theorems become algorithms.

### Definitions
A **graph** G = (V, E) has vertices V and edges E. The **degree** of a vertex is the number of edges at it. A **path** is a sequence of vertices joined by edges; a **cycle** is a path that returns to its start. A graph is **connected** if every pair of vertices is joined by a path.

### The handshake lemma
**Claim.** The sum of all degrees equals twice the number of edges.
**Proof.** Each edge contributes 1 to the degree of each of its two endpoints, so it is counted exactly twice in the sum. ∎

**Corollary.** The number of vertices of odd degree is even.

### Trees
A **tree** is a connected graph with no cycles. The following are equivalent for a graph with n vertices:

- it is a tree;
- it is connected and has exactly n − 1 edges;
- any two vertices are joined by exactly one path;
- it is connected, and removing any edge disconnects it.

**Claim.** A tree with n vertices has n − 1 edges.
**Proof (induction on n).** A single vertex has 0 edges. A tree with n ≥ 2 vertices has a leaf (a vertex of degree 1): follow a path until it cannot be extended; it cannot revisit a vertex, since there are no cycles. Remove the leaf and its edge. What remains is a tree with n − 1 vertices and, by hypothesis, n − 2 edges. Restoring the leaf gives n − 1. ∎

A **spanning tree** of a connected graph is a subgraph that is a tree and includes every vertex. Networks use spanning trees to avoid loops.

### Euler and Hamilton
- An **Euler circuit** uses every **edge** exactly once. Euler proved in 1736 that a connected graph has one **if and only if every vertex has even degree**. It can be found in linear time.
- A **Hamilton cycle** visits every **vertex** exactly once. No efficient test is known; the problem is NP-complete.

Two problems that sound alike, one easy and one apparently intractable. Recognising which side of that line a problem is on is a core skill.

### Colouring
A **colouring** assigns colours to vertices so that adjacent vertices differ. The smallest number needed is the **chromatic number**. Colouring models conflict: scheduling exams so that no student has two at once, or assigning variables to processor registers.

A graph is **bipartite** if it can be coloured with two colours, which holds exactly when it has **no cycle of odd length**. This can be tested with a breadth-first search.

Every **planar** graph (drawable without crossing edges) can be coloured with four colours: the four-colour theorem, proved in 1976 with essential help from a computer.

### Directed graphs
A **directed acyclic graph** (DAG) has a **topological order**: a listing in which every edge points forward. Conversely, a directed graph with a topological order has no cycle. Build systems, spreadsheets and task schedulers depend on this.

### Matchings
A **matching** is a set of edges with no shared vertices: assigning tasks to workers, students to places. **Hall's theorem** states exactly when a bipartite graph has a matching covering one side: every set of k vertices on that side must have at least k neighbours between them.

### Why the theory matters
A theorem tells you what to look for. Knowing that "tree" means "connected with n − 1 edges" gives you a constant-time sanity check. Knowing the even-degree condition turns a search problem into a count.

> Key idea: Many hard-looking questions about networks have clean characterisations. Find the theorem before writing the search.

#LESSON Number theory and modular arithmetic | 14
Number theory, once considered the purest mathematics, is now the basis of cryptography, hashing and error detection.

### Divisibility
a **divides** b (written a | b) if b = a·k for some integer k. A **prime** has exactly two positive divisors, 1 and itself.

**The fundamental theorem of arithmetic:** every integer greater than 1 is a product of primes in exactly one way, apart from order.

**Claim (Euclid).** There are infinitely many primes.
**Proof.** Suppose there were finitely many: p₁, ..., pₙ. Let N = p₁·p₂·...·pₙ + 1. N leaves remainder 1 when divided by each pᵢ, so none of them divides it. But N has some prime factor, which is therefore not on the list. Contradiction. ∎

### The greatest common divisor
**Euclid's algorithm** computes gcd(a, b):

```python
def gcd(a, b):
    while b != 0:
        a, b = b, a % b
    return a
```

It works because any common divisor of a and b also divides a mod b, and conversely, so gcd(a, b) = gcd(b, a mod b). The remainder at least halves every two steps, so it takes O(log n) steps.

**Bézout's identity:** there are integers x and y with a·x + b·y = gcd(a, b). The **extended** Euclidean algorithm finds them.

### Modular arithmetic
a ≡ b (mod m) means m divides a − b: they leave the same remainder. Arithmetic "wraps round", as on a clock.

You may reduce at any point:

```text
(a + b) mod m = ((a mod m) + (b mod m)) mod m
(a · b) mod m = ((a mod m) · (b mod m)) mod m
```

So huge results can be computed without huge intermediate numbers.

### Modular inverses
An **inverse** of a modulo m is a number x with a·x ≡ 1 (mod m). It exists exactly when gcd(a, m) = 1, and the extended Euclidean algorithm finds it. With a prime modulus, every non-zero number has an inverse, so division works: the integers modulo a prime form a **field**.

### Fast exponentiation
Computing aᵉ mod m by multiplying e times is impossible when e has hundreds of digits. **Square and multiply** uses the binary form of e:

```python
def mod_pow(base, exp, mod):
    result = 1 % mod
    base = base % mod
    while exp > 0:
        if exp % 2 == 1:
            result = (result * base) % mod
        base = (base * base) % mod
        exp = exp // 2
    return result
```

This takes O(log e) multiplications.

### Fermat's little theorem
If p is prime and p does not divide a, then

```text
a^(p − 1) ≡ 1 (mod p)
```

It gives inverses (a^(p−2) is the inverse of a) and is the basis of fast **primality tests**. The Miller-Rabin test decides primality of numbers with hundreds of digits in milliseconds, with a negligible chance of error.

### Public-key cryptography
**RSA** in outline: choose two large primes p and q; publish n = p·q and an exponent e. Encryption is c = mᵉ mod n. Decryption uses a secret exponent d, computed from p and q, with (mᵉ)ᵈ ≡ m (mod n). Multiplying p and q is easy. Recovering them from n, **factoring**, has no known efficient algorithm on ordinary computers. Security rests on that asymmetry.

**Diffie-Hellman** key exchange rests on the difficulty of the **discrete logarithm**: given g, p and gˣ mod p, find x.

Both problems could be solved efficiently by a large quantum computer running Shor's algorithm, which is why new algorithms based on different mathematics are being adopted.

### Elsewhere in computing
Hash tables use `hash mod size`. Checksums and check digits use modular sums. Random-number generators use modular recurrences.

> Key idea: Modular arithmetic keeps numbers small while preserving structure. Some operations in it are easy to do and apparently hard to undo, and cryptography is built on that gap.

#LESSON Probability foundations | 14
Probability is the mathematics of uncertainty. Machine learning, randomised algorithms, performance modelling, reliability engineering and cryptography all depend on it.

### The framework
- The **sample space** Ω is the set of all possible outcomes.
- An **event** is a set of outcomes.
- A **probability** P assigns each event a number such that P(Ω) = 1, probabilities are never negative, and for events that cannot both happen, P(A or B) = P(A) + P(B).

When all outcomes are equally likely, P(A) = (outcomes in A) / (all outcomes), so probability becomes counting.

Basic rules:

```text
P(not A)  = 1 − P(A)
P(A or B) = P(A) + P(B) − P(A and B)
```

The complement rule is often the easy route: "at least one" is 1 minus "none".

### Conditional probability
The probability of A given that B has occurred:

```text
P(A | B) = P(A and B) / P(B)
```

Conditioning restricts attention to the outcomes where B holds.

### Independence
A and B are **independent** if P(A and B) = P(A)·P(B): learning one tells you nothing about the other. Independence is an assumption to be justified, not a default. Two servers in the same rack do not fail independently.

### Bayes' theorem
```text
P(A | B) = P(B | A) · P(A) / P(B)
```

It reverses a conditional: from "how likely is the evidence given the hypothesis" to "how likely is the hypothesis given the evidence".

**Example.** A monitoring alert fires for 99% of real outages and for 5% of normal periods. Outages occur in 1% of periods. The alert fires. How likely is a real outage?

```text
P(alert) = 0.99 × 0.01 + 0.05 × 0.99 = 0.0099 + 0.0495 = 0.0594
P(outage | alert) = 0.0099 / 0.0594 ≈ 0.167
```

Only about 17%. The outage is rare, so false alarms from the many normal periods outnumber true alarms. Ignoring the **base rate** is the most common error in reasoning about tests, alerts and classifiers.

The denominator used the **law of total probability**: split the event by cases that cover everything.

### Classic surprises
- **Birthday problem:** with 23 people, the chance that two share a birthday exceeds one half. Compute it as 1 minus the chance that all differ.
- **Monty Hall:** switching wins two thirds of the time, because the host's choice carries information.

Intuition is unreliable in probability. Write down the sample space and compute.

### Probability in algorithms
- **Randomised algorithms** make random choices to avoid bad worst cases: quicksort with a random pivot runs in expected O(n log n) on every input.
- **Hashing** analysis assumes keys spread uniformly.
- **Bloom filters** trade a small, calculable false-positive probability for large memory savings.
- **Load balancing:** choosing the less loaded of two random servers improves balance dramatically over choosing one at random.

> Key idea: Always ask "out of what?". Most probability mistakes come from the wrong sample space or a forgotten base rate.

#LESSON Random variables and distributions | 14
A **random variable** is a number determined by a random outcome: the number of heads in ten tosses, the latency of a request.

### Expectation
The **expected value** is the probability-weighted average:

```text
E[X] = sum of  x · P(X = x)  over all values x
```

A fair die has E[X] = 3.5. Expectation is a long-run average, not a typical value.

**Linearity of expectation:** E[X + Y] = E[X] + E[Y], **always**, even when X and Y are dependent. This is extraordinarily useful.

**Example.** n people each take a random hat from a pile of their n hats. What is the expected number who get their own? Let Xᵢ be 1 if person i does. E[Xᵢ] = 1/n. By linearity the total is n · (1/n) = **1**, whatever n is. No analysis of dependence was needed.

### Variance
**Variance** measures spread:

```text
Var(X) = E[(X − μ)²] = E[X²] − (E[X])²
```

The **standard deviation** σ is its square root, in the same units as X. For **independent** variables, variances add.

### Common discrete distributions
| Distribution | Models | Mean |
|---|---|---|
| Bernoulli(p) | One trial with success probability p | p |
| Binomial(n, p) | Successes in n independent trials | np |
| Geometric(p) | Trials until the first success | 1/p |
| Poisson(λ) | Events in a fixed interval at average rate λ | λ |

If each attempt succeeds with probability p, you expect 1/p attempts. A retry loop against a service that succeeds 80% of the time makes 1.25 attempts on average.

### Continuous distributions
A continuous variable has a **density**: probability is area under the curve.

- **Uniform:** all values in a range equally likely.
- **Exponential:** time between events that occur at a constant average rate. It is **memoryless**: having waited already tells you nothing about how much longer.
- **Normal (Gaussian):** the bell curve, described by mean μ and standard deviation σ. About 68% of values lie within 1σ of the mean, 95% within 2σ and 99.7% within 3σ.

### The law of large numbers
The average of many independent samples approaches the expected value. This is why simulation and sampling work.

### The central limit theorem
The **sum (or average) of many independent random variables is approximately normally distributed**, almost regardless of the distribution of each one. This is why the normal distribution appears everywhere, and why averages of measurements have predictable error.

### Heavy tails
Not everything is normal. Request latencies, file sizes, wealth and popularity often follow **heavy-tailed** distributions, in which extreme values are far more common than a normal curve predicts and a few items account for most of the total. The mean is then misleading and the variance may be enormous. This is why systems are measured with **percentiles**.

### Tail bounds
When you need a guarantee, not an average:

- **Markov's inequality:** for a non-negative variable, P(X ≥ a) ≤ E[X] / a.
- **Chebyshev's inequality:** P(|X − μ| ≥ kσ) ≤ 1/k².
- **Chernoff bounds:** sums of independent variables are concentrated exponentially tightly round their mean.

These are the tools that prove a randomised algorithm is fast "with high probability".

### Queues, briefly
If requests arrive at rate λ and are served at rate μ, **utilisation** is ρ = λ/μ. In the simplest model the average number in the system is ρ/(1 − ρ). At 50% utilisation that is 1; at 90% it is 9; at 99% it is 99. Latency explodes as a system approaches full utilisation, which is why you never plan to run at 100%.

> Key idea: Linearity of expectation holds without independence. It turns many hard-looking problems into a sum of easy ones.

#LESSON Statistics and inference | 14
Probability reasons from a known model to data. **Statistics** reasons backwards, from data to conclusions about the process that produced it.

### Describing data
- **Centre:** the **mean** (sensitive to outliers) and the **median** (robust).
- **Spread:** variance, standard deviation, the interquartile range.
- **Shape:** look at a histogram before computing anything.

Summary statistics can deceive: quite different data sets can share the same mean, variance and correlation. Plot the data.

### Samples and populations
You almost never see the whole **population**; you see a **sample**. Conclusions are sound only if the sample is representative. **Selection bias** is the usual failure: surveying only users who stayed, or measuring only requests that completed.

When estimating the variance of a population from a sample, divide by n − 1, not n, to correct for the fact that the sample mean was estimated from the same data.

### Estimation and confidence intervals
A sample mean estimates the population mean. Its uncertainty is the **standard error**:

```text
standard error = s / √n
```

To halve the uncertainty you need **four times** the data.

A **95% confidence interval** is approximately the estimate plus or minus two standard errors. Its meaning is precise: if you repeated the whole procedure many times, about 95% of the intervals so constructed would contain the true value.

### Hypothesis testing
1. State a **null hypothesis** H₀: there is no effect.
2. Collect data and compute a test statistic.
3. Compute the **p-value**: the probability of data at least this extreme **if H₀ were true**.
4. If the p-value is below a threshold chosen in advance (commonly 0.05), reject H₀.

What a p-value is **not**: it is not the probability that H₀ is true, and not the probability that the result is due to chance.

- A **type I error** is a false positive: rejecting a true null.
- A **type II error** is a false negative: missing a real effect. **Power** is the probability of detecting an effect that exists, and it grows with sample size.

### Statistical and practical significance
With enough data, a trivially small difference becomes statistically significant. Always report the **effect size** and its interval. "Conversion rose by 0.02 percentage points (p = 0.01)" is significant and may be worthless.

### A/B testing
The software industry's experiment. Randomly assign users to the current version (A) or the new one (B) and compare a metric chosen in advance.

Pitfalls:

- **Peeking:** checking repeatedly and stopping when the result looks significant inflates false positives. Fix the sample size beforehand.
- **Multiple comparisons:** test 20 metrics at the 0.05 level and one is expected to pass by chance. Correct for it.
- **Novelty effects** and too-short runs.
- Non-random assignment.

### Correlation and causation
**Correlation** measures how two variables move together, from −1 to 1. It does not show that one causes the other: a third factor (a **confounder**) may drive both, or the direction may be reversed. **Randomised experiments** are the reliable way to establish causation, since randomisation balances confounders on average.

**Simpson's paradox:** a trend present in every subgroup can reverse when the groups are combined. Aggregates hide structure.

### Regression
**Linear regression** fits a line minimising the squared errors. It quantifies relationships and makes predictions, under assumptions that should be checked by plotting the residuals.

### Honest analysis
Decide the question, the metric and the analysis **before** looking at the data. Report everything you tried, not only what worked. Share the data and code.

> In industry: Benchmark comparisons need this rigour too. "Version B was 3% faster" means nothing without repeated runs, the variation between them, and a test of whether the difference exceeds the noise.

#LESSON Vectors and matrices | 14
Linear algebra is the mathematics of data in bulk. Graphics, machine learning, search, signal processing and scientific computing are all built on it.

### Vectors
A **vector** is an ordered list of numbers: a point in space, or a direction with a length.

```text
v = (3, 4)         length (norm):  ‖v‖ = √(3² + 4²) = 5
```

Vectors add component-wise and scale by a number.

### The dot product
```text
u · v = u₁v₁ + u₂v₂ + ... + uₙvₙ = ‖u‖ ‖v‖ cos θ
```

where θ is the angle between them. It measures alignment:

- positive when they point the same way,
- **zero when perpendicular** (orthogonal),
- negative when opposed.

**Cosine similarity**, (u · v) / (‖u‖ ‖v‖), compares direction regardless of length. Search engines and recommendation systems represent documents, images and users as vectors (**embeddings**) and find similar items by cosine similarity.

### Matrices
A **matrix** is a rectangular grid of numbers with m rows and n columns. It can represent a data table, a system of equations, a graph (the adjacency matrix), or a **linear transformation**.

### Matrix multiplication
For A (m × n) and B (n × p), the product AB is m × p, and its entry in row i, column j is the **dot product of row i of A with column j of B**.

```text
| 1  2 |   | 5  6 |   | 1·5 + 2·7   1·6 + 2·8 |   | 19  22 |
| 3  4 | × | 7  8 | = | 3·5 + 4·7   3·6 + 4·8 | = | 43  50 |
```

The inner sizes must match. Multiplication is associative but **not commutative**: in general AB ≠ BA.

Why this definition? A matrix is a function that transforms vectors, and the product AB is the transformation "apply B, then A". Composition of functions is associative and not commutative, and so is matrix multiplication.

### Linear transformations
Multiplying a vector by a matrix transforms it: rotation, scaling, shearing, projection. In two dimensions:

```text
rotate by θ:   |  cos θ   −sin θ |        scale:   | sx  0  |
               |  sin θ    cos θ |                 | 0   sy |
```

Every frame of a three-dimensional game is produced by multiplying millions of vertices by transformation matrices, which is the workload GPUs were built for.

### Special matrices
- The **identity** I leaves vectors unchanged: AI = IA = A.
- The **transpose** Aᵀ swaps rows and columns.
- The **inverse** A⁻¹ undoes A: A⁻¹A = I. Only square matrices can have one, and not all do.
- A **symmetric** matrix equals its transpose.
- An **orthogonal** matrix has perpendicular unit columns; its inverse is its transpose, and it preserves lengths and angles.

### Rank and independence
Vectors are **linearly independent** if none is a combination of the others. The **rank** of a matrix is the number of independent rows (equivalently, columns): the true dimension of the data. A matrix of low rank contains redundancy, which is what compression and recommendation systems exploit.

### Cost
Multiplying two n × n matrices by the definition takes O(n³) operations. Faster algorithms exist in theory (Strassen's is about O(n^2.81)). In practice, heavily optimised libraries (BLAS) and GPUs exploit cache layout and parallelism to reach speeds hand-written loops cannot.

### Neural networks are linear algebra
A layer of a neural network computes `output = f(W·x + b)`: a matrix multiplication, a vector addition and a simple non-linear function. A deep network is many of these composed. Training and running models is, overwhelmingly, matrix multiplication.

> Key idea: A matrix is a function on vectors, and matrix multiplication is function composition. That one idea explains its rules.

#LESSON Linear systems, eigenvalues and decompositions | 14
### Systems of linear equations
```text
2x +  y = 5
 x − 3y = −1
```

is the matrix equation **Ax = b**. **Gaussian elimination** solves it by subtracting multiples of rows to reach a triangular form, then substituting backwards. It takes O(n³) operations.

A system has exactly one solution, none, or infinitely many. For a square matrix, a unique solution exists exactly when A is **invertible**, equivalently when its **determinant** is not zero, equivalently when its columns are linearly independent.

In numerical work, do not compute A⁻¹ to solve a system. Factorise instead (**LU decomposition**): it is faster and more accurate.

### Numerical care
Computers use floating-point arithmetic, so results carry rounding error. A matrix is **ill-conditioned** if small changes in the input cause large changes in the solution; its **condition number** measures this. Sound algorithms use **pivoting** to control the growth of error. Never test floating-point results for exact equality.

### Least squares
Real data rarely fits exactly. With more equations than unknowns, find the x that minimises the squared error ‖Ax − b‖². The solution satisfies the **normal equations** AᵀAx = Aᵀb. This is linear regression, and it is the most used computation in applied statistics.

### Eigenvalues and eigenvectors
For a square matrix A, a non-zero vector v is an **eigenvector** with **eigenvalue** λ if

```text
A v = λ v
```

The matrix only stretches v; it does not turn it. Eigenvectors are the special directions of a transformation, and eigenvalues the stretch factors.

**Example.** For a diagonal matrix with entries 2 and 3, the axes are eigenvectors, with eigenvalues 2 and 3.

Why they matter:

- **Repeated application.** Aᵏ is governed by the eigenvalues. If the largest has magnitude below 1, the process dies away; above 1, it grows. This decides the stability of systems.
- **PageRank.** The importance of web pages is the principal eigenvector of the web's link matrix: the long-run distribution of a random surfer. It is found by **power iteration**: start with any vector and multiply by the matrix repeatedly.
- **Vibration, quantum mechanics, graph partitioning** all reduce to eigenproblems.

A real symmetric matrix has real eigenvalues and perpendicular eigenvectors: the **spectral theorem**.

### The singular value decomposition
Any matrix, of any shape, factorises as

```text
A = U Σ Vᵀ
```

where U and V are orthogonal and Σ is diagonal with non-negative **singular values** in decreasing order. Geometrically: every linear map is a rotation, then a scaling along axes, then another rotation.

The singular values rank the directions by importance. Keeping only the largest k gives the **best possible rank-k approximation** of A.

Applications:

- **Compression:** an image stored as a few hundred singular vectors instead of millions of pixels.
- **Principal component analysis (PCA):** find the directions in which data varies most and project onto them, reducing hundreds of dimensions to a few.
- **Recommendation:** approximate the huge, sparse user-by-item ratings matrix with a low-rank one, revealing latent tastes.
- **Noise reduction** and **search** over text.

### Sparse matrices
Matrices from real problems are often mostly zeros: a web graph, a social network. **Sparse** formats store only the non-zero entries, and **iterative methods** such as conjugate gradient solve systems using only matrix-vector products, never forming the dense matrix.

### In practice
Use a library: NumPy, LAPACK, Eigen. They are decades more refined than anything you will write. Your job is to recognise which decomposition the problem needs.

> Key idea: Decompositions reveal structure. Eigenvectors show a matrix's invariant directions; the SVD ranks the directions of any data by importance.

* It gives the best low-rank approximation, used for compression and dimensionality reduction
- It inverts the matrix
! The largest singular values capture the most important structure.

#LESSON Calculus and optimisation | 14
Calculus is the mathematics of change. For computing its central use is **optimisation**: finding the inputs that make some quantity as small or as large as possible. Training every machine-learning model is an optimisation problem.

### The derivative
The **derivative** f′(x) is the rate at which f changes as x changes: the slope of the curve at that point.

```text
f′(x) = limit as h → 0 of  (f(x + h) − f(x)) / h
```

Rules:

| Function | Derivative |
|---|---|
| xⁿ | n·xⁿ⁻¹ |
| eˣ | eˣ |
| ln x | 1/x |
| f + g | f′ + g′ |
| f · g | f′g + fg′ |
| f(g(x)) | f′(g(x)) · g′(x) (the **chain rule**) |

### Finding minima
At a minimum or maximum of a smooth function, the slope is zero: f′(x) = 0. The second derivative distinguishes them: positive means a minimum (the curve bends upward).

**Example.** f(x) = x² − 6x + 10. Then f′(x) = 2x − 6 = 0 gives x = 3, and f″ = 2 > 0, so the minimum is f(3) = 1.

### Several variables
For a function of many variables, a **partial derivative** measures the change with respect to one variable while the others are held fixed. The **gradient** ∇f is the vector of all the partial derivatives.

The gradient **points in the direction of steepest increase**, and its length is the rate of that increase.

### Gradient descent
To minimise f, repeatedly step against the gradient:

```text
x ← x − η · ∇f(x)
```

η is the **learning rate**.

```diagram
   loss
    |  \
    |   \         each step moves downhill
    |    \__
    |       \___
    |           \______.  minimum
    +-------------------------- parameter
```

- Too small a learning rate: painfully slow.
- Too large: overshoots and may diverge.

For a **convex** function (bowl-shaped, with a single minimum) gradient descent finds the global minimum. Neural-network losses are not convex, yet gradient descent works remarkably well in practice.

**Stochastic gradient descent** estimates the gradient from a small random batch of the data instead of all of it. Each step is cheap and noisy; overall it is far faster.

### The chain rule and backpropagation
A neural network is a composition of functions. The chain rule gives the derivative of the loss with respect to every parameter by multiplying local derivatives backwards through the layers. This is **backpropagation**. **Automatic differentiation** applies the chain rule mechanically to arbitrary code, and is the core of every deep-learning framework.

### Integration
The **integral** is the accumulated total: the area under a curve. The **fundamental theorem of calculus** says integration and differentiation are inverse operations. In computing, integrals give probabilities from densities and expected values of continuous variables. Most real integrals are computed numerically: by summing small slices, or by **Monte Carlo** sampling.

### Series and approximation
A **Taylor series** approximates a smooth function near a point by a polynomial built from its derivatives. For small x, eˣ ≈ 1 + x and sin x ≈ x. Linear approximation near a point is what makes gradient-based methods work.

### Growth rates, revisited
Calculus gives precise meaning to Big O: f grows more slowly than g if f(n)/g(n) → 0. Logarithms grow more slowly than any power of n; any power more slowly than any exponential.

### Constrained optimisation
Real problems have constraints: budgets, capacities. **Lagrange multipliers** handle equality constraints. **Linear programming** optimises a linear objective under linear constraints and solves scheduling, routing and allocation problems in practice.

> Key idea: The gradient tells you which way is uphill. Walk the other way, repeatedly, and you have the algorithm that trains modern AI.

@solution
def mean(xs):
    total = 0
    for x in xs:
        total = total + x
    return total / len(xs)


def variance(xs):
    m = mean(xs)
    total = 0
    for x in xs:
        total = total + (x - m) * (x - m)
    return total / len(xs)


def dot(u, v):
    total = 0
    for i in range(len(u)):
        total = total + u[i] * v[i]
    return total


def transpose(m):
    if len(m) == 0:
        return []
    result = []
    for j in range(len(m[0])):
        row = []
        for i in range(len(m)):
            row.append(m[i][j])
        result.append(row)
    return result


def mat_mul(a, b):
    result = []
    for i in range(len(a)):
        row = []
        for j in range(len(b[0])):
            total = 0
            for k in range(len(b)):
                total = total + a[i][k] * b[k][j]
            row.append(total)
        result.append(row)
    return result


def bayes(prior, true_positive_rate, false_positive_rate):
    positive = true_positive_rate * prior + false_positive_rate * (1 - prior)
    return round(true_positive_rate * prior / positive, 4)


def gradient_step(x, learning_rate):
    return x - learning_rate * 2 * (x - 3)

#LESSON Finite automata and regular languages | 14
The **theory of computation** asks what can be computed at all, and with what resources. It begins with the simplest model of a machine.

### Languages
An **alphabet** is a finite set of symbols. A **string** is a finite sequence of them. A **language** is a set of strings. "Does this input have property P?" is the question of whether a string belongs to a language, so languages are a precise way to talk about problems.

### Deterministic finite automata
A **DFA** has a finite set of states, one **start state**, some **accepting states**, and a **transition function** giving exactly one next state for each state and symbol. It reads the input once, left to right, and accepts if it finishes in an accepting state.

A DFA accepting binary strings with an even number of 1s:

```diagram
            1
   --> (even) ----> (odd)
        ^  \   <----  /  \
        |   0    1       0
        +---+            +---> (stays odd)
   accepting state: even
```

The machine has **no memory except its current state**. That is its whole power and its whole limit.

### Non-determinism
An **NFA** may have several possible next states, or none, for a symbol. It accepts if **some** sequence of choices leads to an accepting state. Think of it as exploring all paths at once.

NFAs are often much smaller and easier to design. They are not more powerful:

**Theorem.** Every NFA has an equivalent DFA.
**Proof idea (subset construction).** Let each state of the DFA be a **set** of NFA states: the set of all states the NFA could be in. Since the NFA has n states, the DFA needs at most 2ⁿ. ∎

The exponential blow-up can really occur, which is why regular-expression engines choose carefully between simulating the NFA directly and building the DFA.

### Regular expressions
A **regular expression** builds languages from symbols using union (a|b), concatenation (ab) and repetition (a*).

**Kleene's theorem.** A language is described by a regular expression **if and only if** it is accepted by a finite automaton.

These are the **regular languages**. They are closed under union, intersection, complement and concatenation: combining regular languages in these ways gives regular languages.

### What finite automata cannot do
Consider L = { 0ⁿ1ⁿ : n ≥ 0 }: some 0s followed by the same number of 1s.

**Claim.** L is not regular.
**Proof.** Suppose a DFA with k states accepts L. Feed it 0ᵏ followed by 1ᵏ. While reading the k zeros it passes through k + 1 states, so by the pigeonhole principle some state repeats: after i zeros and after j zeros with i < j. From that state, reading 1ⁱ leads to acceptance (since 0ⁱ1ⁱ is in L). But then 0ʲ1ⁱ, which reaches the same state, is also accepted, and it is not in L. Contradiction. ∎

The general form of this argument is the **pumping lemma**. The intuition: a finite machine cannot count without bound.

Consequences: no true regular expression can match balanced parentheses or properly nested HTML. That needs a more powerful model.

### In practice
Lexers, input validation, network protocol states, text search and hardware control circuits are all finite automata. A regular language can be recognised in one pass, in linear time and constant memory.

> Key idea: A finite automaton is computation with a fixed, finite memory. It handles patterns and cannot count without limit.
#Q What is the only memory a finite automaton has?

* Its current state
- An unbounded tape
! With finitely many states it can remember only a bounded amount.
#Q Why is the language of strings 0ⁿ1ⁿ not regular?

* Recognising it requires counting an unbounded number of 0s, which a machine with finitely many states cannot do
- It uses two symbols
! The pigeonhole principle forces two different counts into the same state.

#LESSON Context-free grammars and pushdown automata | 13
To recognise nested structure, a machine needs more memory than a fixed set of states. Add a **stack**.

### Context-free grammars
A **context-free grammar** (CFG) has rules that rewrite a single non-terminal into a string of terminals and non-terminals.

```text
S -> 0 S 1
S -> (empty)
```

generates exactly 0ⁿ1ⁿ: each use of the first rule adds a matched pair. Balanced parentheses:

```text
S -> ( S ) S
S -> (empty)
```

A **derivation** applies rules from the start symbol until only terminals remain. The steps form a **parse tree**. The set of strings a grammar can derive is its language, and such languages are **context-free**.

"Context-free" means a rule applies to a non-terminal wherever it appears, whatever surrounds it.

### Pushdown automata
A **pushdown automaton** (PDA) is a finite automaton with a stack. Each move may read an input symbol, pop the top of the stack and push symbols.

To recognise 0ⁿ1ⁿ: push a marker for each 0; pop one for each 1; accept if the stack empties exactly as the input ends. The stack supplies the unbounded count.

**Theorem.** A language is context-free if and only if some pushdown automaton accepts it.

This is the theoretical basis of parsing: every parser is, in effect, a pushdown automaton, and a recursive-descent parser uses the program's call stack as its stack.

### Ambiguity
A grammar is **ambiguous** if a string has two different parse trees.

```text
E -> E + E | E * E | n
```

gives `n + n * n` two trees, with different meanings. The grammar can be rewritten in layers to remove the ambiguity. Some context-free languages are **inherently ambiguous**: every grammar for them is. And whether a given grammar is ambiguous is **undecidable** in general.

### Determinism matters here
Unlike finite automata, non-deterministic pushdown automata are strictly **more** powerful than deterministic ones. The language of even-length palindromes needs non-determinism, since the machine must guess where the middle is. Programming languages are designed to be **deterministic** context-free, so that they can be parsed in linear time.

General context-free parsing (the CYK and Earley algorithms) takes O(n³) time.

### Limits of context-free languages
A single stack is not enough for everything.

**Claim.** L = { aⁿbⁿcⁿ : n ≥ 0 } is not context-free.
**Intuition.** The stack can match the a's against the b's, but in doing so it is emptied, and nothing remains to check the c's. The formal proof uses the pumping lemma for context-free languages.

Requirements such as "every variable is declared before use" or "a call has the same number of arguments as the definition" are not context-free either. That is why compilers check them in a separate semantic phase, after parsing.

### The Chomsky hierarchy
| Class | Machine | Example |
|---|---|---|
| Regular | Finite automaton | a*b* |
| Context-free | Pushdown automaton | aⁿbⁿ |
| Context-sensitive | Linear-bounded automaton | aⁿbⁿcⁿ |
| Recursively enumerable | Turing machine | Any computable language |

Each class strictly contains the one above it. More memory, organised more flexibly, recognises more languages.

### What happens with two stacks?
A machine with **two** stacks can simulate a tape, moving left and right by transferring symbols between them. It is as powerful as a Turing machine, the subject of the next lesson. The jump from one stack to two is the jump from parsing to general computation.

> Key idea: A stack lets a machine match nested structure. That one addition is the difference between a lexer and a parser.
#Q What does a pushdown automaton have that a finite automaton lacks?
- More states
* A stack
- Random access memory
! The stack provides unbounded last-in, first-out memory.
#Q Why are checks such as "variables must be declared before use" performed after parsing?
- They are too slow for the parser
* Such constraints cannot be expressed by a context-free grammar
- Parsers cannot read identifiers
! They require context that a single stack cannot track.

#LESSON Turing machines and the Church-Turing thesis | 14
In 1936, before any electronic computer existed, Alan Turing defined a simple abstract machine in order to make precise the idea of "a procedure that can be carried out mechanically".

### The machine
A **Turing machine** has:

- an infinite **tape** divided into cells, each holding a symbol;
- a **head** that reads and writes one cell and moves one step left or right;
- a finite set of **states**, including accepting and rejecting states;
- a **transition function**: given the state and the symbol under the head, it specifies the symbol to write, the direction to move and the next state.

```diagram
        ... | _ | 1 | 0 | 1 | 1 | _ | _ | ...
                      ^
                     head         state: q3
```

It starts with the input on the tape and runs until it reaches an accepting or rejecting state. Or it **never halts**. That third possibility is essential, and unavoidable.

### What it can do
Anything you can program. A Turing machine can add, sort, simulate a finite automaton or a pushdown automaton, and recognise aⁿbⁿcⁿ by crossing off one a, one b and one c on each pass.

Variations do not add power: several tapes, several heads, a two-dimensional tape, non-determinism. Each can be simulated by the basic machine, possibly more slowly.

### The universal machine
Turing showed that there is a single **universal Turing machine** U that takes as input a description of any machine M together with an input w, and simulates M on w.

This is the idea of the **stored-program computer**: programs are data. One machine can run any program. Interpreters, virtual machines and operating systems are universal machines.

### The Church-Turing thesis
In the same years, other definitions of "computable" were proposed: Church's lambda calculus, Gödel's recursive functions, Post's systems. They looked nothing alike. **All were proved equivalent**: each computes exactly the same functions.

> The Church-Turing thesis: every function that can be computed by any effective mechanical procedure can be computed by a Turing machine.

This is not a theorem, because "effective procedure" is an informal notion. It is a claim about the world, supported by the fact that every reasonable model ever proposed, including quantum computers, computes the same set of functions.

### Turing completeness
A system is **Turing complete** if it can simulate a Turing machine. Every general-purpose programming language is. So, sometimes by accident, are spreadsheets, some games, type systems of several languages, and CSS combined with HTML.

Consequences:

- All these languages can compute exactly the same things. They differ in convenience and efficiency, never in what is possible.
- Any Turing-complete system inherits the limits of computation. If your configuration language is Turing complete, no tool can decide in general whether a configuration terminates. This is a reason to prefer deliberately **less** powerful languages for configuration, validation and queries.

### Decidable and recognisable
- A language is **decidable** if some Turing machine halts on every input and answers correctly.
- A language is **recognisable** (recursively enumerable) if some machine accepts every string in it, but may run for ever on strings outside it.

Decidable problems are those with a real algorithm: one that always finishes. The next lesson shows that some precisely stated problems are not decidable, and that this is a limit on every computer that can ever be built.

### Efficiency
The thesis concerns what can be computed, not how fast. The **extended** thesis says all reasonable models can simulate each other with at most polynomial slowdown. Quantum computers appear to challenge that version for certain problems, such as factoring.

> Key idea: Every general-purpose computer and language is equivalent in what it can compute. The limits found for Turing machines are limits for everything.
#Q What does a universal Turing machine do?
- Computes faster than any other machine
* Takes a description of any Turing machine and an input, and simulates that machine on that input
- Solves every problem
! It is the theoretical basis of the stored-program computer.
#Q What does it mean for a programming language to be Turing complete?
- It has no bugs
* It can compute everything a Turing machine can
- It runs on any hardware
! All Turing-complete languages are equivalent in computational power.

#LESSON Undecidability and the halting problem | 15
There are problems that no program can solve. Not "no program yet", and not "too slow". No algorithm exists, and this can be **proved**.

### The halting problem
Given a program P and an input x, does P eventually halt when run on x, or does it run for ever?

A tool that answered this would be invaluable. It cannot exist.

**Theorem (Turing, 1936).** The halting problem is undecidable.

**Proof.** Suppose, for contradiction, that a program `halts(P, x)` exists which always returns true or false correctly. Use it to write:

```js
function paradox(P) {
  if (halts(P, P)) {
    while (true) {}      // loop for ever
  } else {
    return;              // halt
  }
}
```

Now run `paradox(paradox)`.

- If `halts(paradox, paradox)` returns **true**, then `paradox` loops for ever on that input. So it does not halt, and `halts` was wrong.
- If it returns **false**, then `paradox` returns at once. So it halts, and `halts` was wrong.

Either way `halts` gives a wrong answer, contradicting the assumption that it is always correct. Therefore no such program exists. ∎

This is a **diagonal argument**, the same idea Cantor used to show that the real numbers cannot be listed. A program is fed its own description, and made to do the opposite of what is predicted.

Note what the theorem does **not** say. Many particular programs can be shown to halt. What is impossible is one method that works for **every** program.

### Reductions
To prove another problem undecidable, show that if you could solve it, you could solve the halting problem. This is a **reduction**.

**Claim.** It is undecidable whether a program ever prints "hello".
**Proof.** Given P and x, build a program Q that runs P on x (suppressing its output) and then prints "hello". Q prints "hello" exactly when P halts on x. A decider for the printing problem would therefore decide halting. ∎

### Rice's theorem
> Every non-trivial property of the **behaviour** of programs is undecidable.

"Non-trivial" means some programs have the property and some do not. "Behaviour" means what the program computes, not how its text looks.

So all of these are undecidable in general:

- Does this program ever crash?
- Are these two programs equivalent?
- Does this function ever return a negative number?
- Is this code free of security vulnerabilities?
- Is this line of code ever reached?
- Does this program contain a virus?

### Living with undecidability
This does not make program analysis useless. It defines what it can be. Every practical tool takes one of these routes:

- **Approximate soundly.** A type checker rejects some programs that would in fact run correctly. It never accepts a bad one. False alarms are the price.
- **Approximate unsoundly.** Linters and bug finders report likely problems and miss some.
- **Restrict the language.** SQL without recursion, regular expressions and total functional languages are deliberately not Turing complete, so questions about them are decidable.
- **Ask for help.** Verification tools require the programmer to supply invariants.
- **Time out.** Run the analysis for a while and give up.

Understanding this explains why static analysers give false positives, why a perfect malware detector cannot exist, and why compilers cannot optimise perfectly.

### Other undecidable problems
- Whether a context-free grammar is ambiguous.
- **Hilbert's tenth problem:** whether a polynomial equation with integer coefficients has an integer solution.
- The Post correspondence problem and various tiling problems.

### Gödel
A related result, **Gödel's incompleteness theorem**, shows that any consistent formal system able to express arithmetic contains true statements it cannot prove. Mathematics, like computation, has limits that are intrinsic and provable.

> Key idea: Some well-defined questions have no algorithm. Every tool that reasons about programs must approximate, restrict or give up, and knowing which it does tells you how to use it.
#Q What does the undecidability of the halting problem state?
- No program can be proved to halt
* No single algorithm can decide correctly, for every program and input, whether it halts
- Halting takes exponential time
! Individual cases can be decided; a universal method cannot exist.
#Q A vendor claims a tool that detects every program containing malicious behaviour with no false alarms. What does Rice's theorem imply?
- The tool must be slow
* Such a tool cannot exist, since any non-trivial behavioural property of programs is undecidable
- The tool works only for small programs
! Real tools must accept false positives, false negatives or both.

#LESSON Complexity: P, NP and intractability | 15
Among the problems that can be solved, some can be solved in practice and some, as far as anyone knows, cannot. **Complexity theory** classifies problems by the resources they need.

### P
**P** is the class of decision problems solvable in **polynomial time**: O(nᵏ) for some constant k. Sorting, shortest paths, matching, primality testing and linear programming are in P. P is the working definition of "efficiently solvable". The definition is robust: it does not depend on the machine model or the programming language.

Exponential time is a different world. At n = 100, n³ is a million operations; 2ⁿ is about 10³⁰, far beyond any computer.

### NP
**NP** is the class of decision problems for which a "yes" answer can be **verified** in polynomial time, given a suitable **certificate**.

- **Satisfiability (SAT):** is there an assignment of true and false that makes this Boolean formula true? Certificate: the assignment. Checking it is easy. Finding it seems hard.
- **Hamilton cycle:** certificate: the cycle.
- **Subset sum:** do some of these numbers add up to the target? Certificate: the subset.
- **Sudoku** on an n² × n² board: certificate: the completed grid.

NP stands for "non-deterministic polynomial", **not** "non-polynomial". Every problem in P is also in NP.

### The P versus NP question
Is every problem whose solutions can be checked quickly also one whose solutions can be **found** quickly?

Nobody knows. It is the most important open problem in computer science, with a million-dollar prize. Almost everyone believes P ≠ NP, since decades of effort have produced no polynomial algorithm for any of thousands of equivalent hard problems. There is no proof.

### NP-completeness
A problem is **NP-hard** if every problem in NP can be reduced to it in polynomial time: it is at least as hard as everything in NP. It is **NP-complete** if it is NP-hard and itself in NP.

**The Cook-Levin theorem (1971):** SAT is NP-complete.

From there, reductions spread. To prove a new problem X NP-hard, reduce a known NP-complete problem **to** X: show that an efficient algorithm for X would give one for the known problem.

```diagram
   known hard problem A  --(polynomial-time transformation)-->  your problem X

   if X were easy, A would be easy; A is believed hard; so X is believed hard
```

The direction matters. Reducing X to SAT shows only that X is no harder than SAT.

Thousands of problems are NP-complete: 3-SAT, graph colouring, travelling salesman (decision form), vertex cover, clique, knapsack, bin packing, scheduling with constraints. **They are all equivalent**: a polynomial algorithm for any one would solve all of them and prove P = NP.

### What to do with a hard problem
Recognising that your problem is NP-hard is valuable. It tells you to stop looking for a perfect efficient algorithm. Then:

- **Solve small instances exactly.** Exponential time is fine for n = 20.
- **Exploit structure.** Your instances may be a special case that is easy: trees, planar graphs, small parameters.
- **Approximate.** Find a solution provably within some factor of the best.
- **Use heuristics.** Local search, simulated annealing and genetic algorithms give good answers with no guarantee.
- **Use a solver.** Modern SAT, SMT and integer-programming solvers handle industrial instances with millions of variables, because real instances are rarely worst cases.
- **Change the problem.**

### Other classes
- **co-NP:** problems whose "no" answers are easily verified.
- **PSPACE:** solvable with polynomial memory. Contains NP. Includes many game-playing problems.
- **EXPTIME:** solvable in exponential time. Provably larger than P.
- **BPP:** solvable efficiently with randomness and a small probability of error.
- **BQP:** solvable efficiently by a quantum computer. It contains factoring, and is not believed to contain the NP-complete problems.

### Cryptography depends on hardness
Encryption is secure only if some problems are hard on average. If P = NP, nearly all of public-key cryptography would be breakable. Our digital security rests on an unproven conjecture.

> Key idea: NP-complete problems are all the same problem in disguise. Learn to recognise the disguise, and you will know when to stop searching for an exact efficient algorithm and start approximating.
#Q What defines the class NP?

* Decision problems whose "yes" answers can be verified in polynomial time given a certificate
- Problems with no solution
! NP is about efficient verification.
#Q To show that a new problem X is NP-hard, what must you do?
- Reduce X to a known NP-complete problem
* Reduce a known NP-complete problem to X in polynomial time
- Show that X takes a long time on your computer
! An efficient solution to X would then solve the known hard problem.

@solution
function runDFA(dfa, input) {
  let state = dfa.start;
  for (const symbol of input) {
    const row = dfa.transitions[state];
    if (!row || row[symbol] === undefined) return false;
    state = row[symbol];
  }
  return dfa.accept.includes(state);
}

function runNFA(nfa, input) {
  let current = new Set([nfa.start]);
  for (const symbol of input) {
    const next = new Set();
    for (const state of current) {
      const row = nfa.transitions[state];
      const targets = (row && row[symbol]) || [];
      for (const t of targets) { next.add(t); }
    }
    current = next;
  }
  for (const state of current) {
    if (nfa.accept.includes(state)) return true;
  }
  return false;
}

function isBalanced(text) {
  const pairs = { ")": "(", "]": "[", "}": "{" };
  const stack = [];
  for (const c of text) {
    if (c === "(" || c === "[" || c === "{") {
      stack.push(c);
    } else if (pairs[c]) {
      if (stack.pop() !== pairs[c]) return false;
    }
  }
  return stack.length === 0;
}

function countReachable(dfa) {
  const seen = new Set([dfa.start]);
  const queue = [dfa.start];
  while (queue.length > 0) {
    const state = queue.shift();
    const row = dfa.transitions[state] || {};
    for (const symbol of Object.keys(row)) {
      if (!seen.has(row[symbol])) {
        seen.add(row[symbol]);
        queue.push(row[symbol]);
      }
    }
  }
  return seen.size;
}

#LESSON Amortised analysis and advanced data structures | 14
Worst-case analysis of a single operation can be misleading. Some operations are occasionally expensive and usually cheap. **Amortised analysis** bounds the **average cost per operation over any sequence**, with no probability involved. It is a guarantee, not an expectation.

### The dynamic array
Appending to a full array of capacity n requires copying all n elements. Yet appending is called O(1). Why?

Suppose the capacity doubles when full. Over n appends, copies occur at sizes 1, 2, 4, 8, ..., and the total copying is

```text
1 + 2 + 4 + ... + n  <  2n
```

So n appends cost fewer than 3n steps in total: **amortised O(1)** each.

**The accounting method.** Charge each append 3 units: 1 for the write, and 2 saved as credit on the element. When the array doubles, each element copied is paid for by saved credit. The bank balance never goes negative, so 3 per operation suffices.

Growing by a fixed amount instead would give O(n) amortised cost. The geometric growth is essential.

**The potential method** generalises this: define a potential function on the data structure, and let the amortised cost be the actual cost plus the change in potential.

### Union-find
The **disjoint-set** structure maintains a partition of elements into groups, with two operations: `find(x)` returns the representative of x's group, and `union(x, y)` merges two groups.

Each group is a tree with parent pointers; the root is the representative. Two optimisations:

- **Union by rank:** attach the shorter tree under the taller.
- **Path compression:** during `find`, point every node visited directly at the root.

```diagram
   before find(d):   a <- b <- c <- d        after:   a <- b
                                                      a <- c
                                                      a <- d
```

Together they give an amortised cost per operation of O(α(n)), where α is the inverse Ackermann function, which is at most 4 for any input that could exist in the universe. For practical purposes it is constant. The proof is one of the most intricate in the analysis of algorithms.

Uses: Kruskal's minimum spanning tree, connected components as edges arrive, image segmentation, type unification in compilers.

### Heaps beyond binary
A binary heap gives insert and extract-min in O(log n). A **Fibonacci heap** achieves O(1) amortised insert and decrease-key, which improves the theoretical bound of Dijkstra's algorithm to O(E + V log V). Its constant factors are large, so simpler heaps usually win in practice.

### Balanced search trees
- **Red-black trees** and **AVL trees** keep height O(log n) by rotations.
- **B-trees** have many keys per node, matching disk pages; they index databases.
- **Splay trees** move each accessed node to the root. No single operation is guaranteed fast, but any sequence of m operations takes O(m log n): an amortised bound, and they adapt to skewed access patterns.
- **Skip lists** use randomness in place of rebalancing, giving expected O(log n) with simple code.

### Range queries
- A **segment tree** answers range queries (sum, minimum) and supports updates in O(log n).
- A **Fenwick tree** does prefix sums in O(log n) with a remarkably short implementation.

### Probabilistic structures
When exact answers cost too much memory:

- A **Bloom filter** tests set membership with no false negatives and a tunable false-positive rate, in a few bits per element.
- **Count-min sketch** estimates frequencies in a stream.
- **HyperLogLog** estimates the number of distinct elements among billions using kilobytes.

### Persistent structures
A **persistent** data structure preserves its previous versions when modified, by sharing unchanged parts. Functional languages and version-control systems depend on them.

> Key idea: Amortised analysis shows that occasional expensive operations are paid for by many cheap ones. It is a worst-case guarantee over a sequence, with no assumption of randomness.

#LESSON Graph algorithms in depth | 15
### Minimum spanning trees
Given a connected, weighted, undirected graph, a **minimum spanning tree** (MST) connects all vertices with the least total edge weight.

**The cut property.** For any division of the vertices into two groups, the lightest edge crossing between them belongs to some MST.
**Proof (exchange argument).** Let e be the lightest crossing edge and T an MST without it. Adding e to T creates a cycle, which must cross the cut at another edge f. Since e is no heavier than f, replacing f with e gives a spanning tree that is no heavier. So it is also an MST, and it contains e. ∎

Both classic algorithms are greedy and justified by this property.

- **Kruskal:** sort the edges; add each edge unless it would form a cycle. Detect cycles with union-find. O(E log E).
- **Prim:** grow one tree, always adding the lightest edge leaving it, using a priority queue. O(E log V).

### Shortest paths
- **Dijkstra:** non-negative weights. Repeatedly settle the unsettled vertex nearest the source. O((V + E) log V) with a heap. It is correct because, with non-negative weights, the nearest unsettled vertex cannot later be reached more cheaply.
- **Bellman-Ford:** allows negative weights. Relax every edge V − 1 times. O(VE). One further pass detects a **negative cycle**, in which case no shortest path exists.
- **Floyd-Warshall:** all pairs, by dynamic programming over permitted intermediate vertices. O(V³).
- **A\*:** Dijkstra guided by a **heuristic** estimating the remaining distance. If the heuristic never overestimates (**admissible**), the result is optimal. It is the standard for route planning and games.

### Network flow
A **flow network** has a source, a sink and capacities on its edges. The **maximum flow** problem asks how much can be sent from source to sink.

**Ford-Fulkerson method:** repeatedly find an **augmenting path** with spare capacity in the **residual graph** and push flow along it. The residual graph includes reverse edges, which allow earlier decisions to be undone.

**The max-flow min-cut theorem:** the maximum flow equals the minimum total capacity of a set of edges whose removal separates the source from the sink.

```diagram
   source ==10==> a ==4==> sink          the cut {a->sink, b->sink} has capacity 4 + 9 = 13
      \\                                  the cut {source->a, source->b} has capacity 10 + 5 = 15
       ==5==> b ==9==> sink               maximum flow = 4 + 5 = 9  (limited by a->sink and source->b)
```

This duality is powerful: a flow of value k together with a cut of capacity k proves both are optimal.

Many problems **reduce** to flow: bipartite matching (assigning workers to tasks), finding edge-disjoint paths, image segmentation, project selection. Recognising a flow problem in disguise is an important skill.

### Strongly connected components
In a directed graph, a **strongly connected component** is a maximal set of vertices each reachable from the others. Tarjan's and Kosaraju's algorithms find them in O(V + E). Collapsing each component gives a DAG. This underlies dependency-cycle detection and solving 2-SAT in linear time.

### Matching
A **maximum matching** in a bipartite graph is found by flow or by the Hopcroft-Karp algorithm in O(E√V). The **Hungarian algorithm** finds the minimum-cost assignment. For stable pairings with preferences on both sides, the **Gale-Shapley** algorithm always finds a **stable matching**, and is used to assign medical graduates to hospitals.

### Proving greedy algorithms correct
Greedy algorithms are simple and often wrong. Two proof patterns establish correctness:

- **Exchange argument:** take any optimal solution and show it can be transformed, step by step and without getting worse, into the greedy one.
- **Greedy stays ahead:** show by induction that after each step the greedy solution is at least as good as any other.

If you cannot find such a proof, look for a counterexample. There usually is one.

> Key idea: A greedy choice needs a proof. The cut property and the exchange argument are what turn a plausible heuristic into an algorithm.

#LESSON Dynamic programming in depth | 14
**Dynamic programming** (DP) solves a problem by combining the solutions of overlapping subproblems, computing each once. It applies when a problem has:

- **Optimal substructure:** an optimal solution is built from optimal solutions to subproblems.
- **Overlapping subproblems:** the same subproblems recur.

### A method
1. **Define the subproblem** precisely, in words. This is the hard part. "dp[i][j] is the length of the longest common subsequence of the first i characters of A and the first j of B."
2. **Write the recurrence** relating a subproblem to smaller ones.
3. **Identify the base cases.**
4. **Choose the order** of computation so that dependencies come first.
5. **Analyse:** number of subproblems × time per subproblem.
6. **Reconstruct** the solution, if needed, by recording choices.

### Longest common subsequence
```text
dp[i][j] = 0                                if i = 0 or j = 0
         = dp[i−1][j−1] + 1                 if A[i] = B[j]
         = max(dp[i−1][j], dp[i][j−1])      otherwise
```

O(nm) time. It underlies `diff`, version control and DNA comparison.

**Why the recurrence is right.** If the last characters match, some optimal solution uses that match (an exchange argument). If they differ, at least one of them is unused, so drop it.

### Edit distance
The minimum number of insertions, deletions and substitutions to turn one string into another. The recurrence considers the three possible last operations. Used in spell-checking and fuzzy search.

### Knapsack
Items with weights and values, and a capacity W. Maximise the value.

```text
dp[i][w] = max( dp[i−1][w],                        skip item i
                dp[i−1][w − weightᵢ] + valueᵢ )    take item i, if it fits
```

Time O(nW). This looks polynomial but is **pseudo-polynomial**: W is a number, and its size as input is log W bits. Knapsack is NP-hard. The DP is efficient only when the numbers are small.

### Other shapes of DP
- **Interval DP:** dp[i][j] over a contiguous range, such as the optimal order of matrix multiplications.
- **DP on trees:** combine the children's answers at each node, for example the maximum independent set in a tree.
- **Bitmask DP:** a subproblem is a subset, encoded as bits. The Held-Karp algorithm solves the travelling salesman problem in O(n²·2ⁿ), far better than n! and still exponential.
- **DP over DAGs:** every DP is a shortest- or longest-path computation on the graph of its subproblems.
- **Digit DP, probability DP,** and more.

### Reducing memory
If each row depends only on the previous one, keep two rows, or one updated in the right order. LCS drops from O(nm) memory to O(min(n, m)).

### Top-down or bottom-up
**Memoisation** (top-down) is recursion with a cache: natural to write and computes only what is needed. **Tabulation** (bottom-up) fills a table with loops: no recursion overhead and easier to optimise for memory.

### DP versus greedy
Greedy commits to one choice at each step. DP considers all choices and keeps the best. Coin change with coins 1, 3 and 4 for amount 6: greedy takes 4 + 1 + 1 (three coins); DP finds 3 + 3 (two). When a greedy choice cannot be proved safe, DP is the fallback.

### Where DP hides
Sequence alignment in bioinformatics, the Viterbi algorithm in speech recognition and error correction, optimal line breaking in typesetting, query optimisation in databases, and the Bellman equation at the heart of reinforcement learning.

> Key idea: The whole difficulty of dynamic programming is choosing the subproblem. State it in one precise sentence before writing any code.
#Q What two properties must a problem have for dynamic programming to apply?
- Sorted input and unique keys
* Optimal substructure and overlapping subproblems
- A greedy choice and a base case
! Subproblem solutions combine and recur.
#Q Why is the O(nW) knapsack algorithm called pseudo-polynomial?
- It is not correct
* Its running time depends on the numeric value W, which is exponential in the number of bits needed to write W
- It uses too much memory
! Polynomial in the value, not in the input length.

#LESSON Hard problems: approximation and randomisation | 14
When a problem is NP-hard, you change what you ask for. Give up exactness, or certainty, or generality, and efficient algorithms often reappear.

### Approximation algorithms
An **α-approximation** algorithm runs in polynomial time and always returns a solution within a factor α of the optimum. The guarantee is proved, not hoped for.

**Vertex cover.** Choose the fewest vertices such that every edge has at least one endpoint chosen.

*Algorithm:* repeatedly pick any uncovered edge and add **both** its endpoints.

**Claim.** The result is at most twice the optimum.
**Proof.** The edges picked share no endpoints. Any vertex cover, including the optimal one, must contain at least one endpoint of each. So the optimum has at least as many vertices as edges picked, and the algorithm used exactly twice that number. ∎

The proof never needed to know the optimal solution. It bounded the optimum from below. That is the standard technique.

**Travelling salesman with the triangle inequality.** Build a minimum spanning tree, walk round it, and skip repeated vertices. The tour is at most twice the optimum, because the MST weighs no more than the optimal tour. Christofides' algorithm improves this to 1.5.

**Set cover.** Greedily choose the set covering the most uncovered elements. This achieves a factor of about ln n, and it is known that no polynomial algorithm does substantially better unless P = NP.

Problems differ in how well they can be approximated:

- Some have a **polynomial-time approximation scheme**: within (1 + ε) for any ε > 0. Knapsack is one.
- Some have a constant factor and no better (vertex cover).
- Some cannot be approximated within any constant (general travelling salesman, clique).

### Randomised algorithms
An algorithm that tosses coins.

- **Las Vegas** algorithms are always correct; their running time is random. Quicksort with a random pivot: expected O(n log n) on **every** input. No adversary can construct a bad input, since the bad cases depend on the algorithm's private random choices.
- **Monte Carlo** algorithms have bounded running time and may err with small probability. Repeating k times independently drives the error down exponentially.

**Primality testing (Miller-Rabin).** Each round wrongly declares a composite number prime with probability at most 1/4. After 40 rounds the error is below 2⁻⁸⁰, far smaller than the chance of a hardware fault.

**Karger's minimum cut.** Repeatedly contract a random edge until two vertices remain. One run succeeds with probability at least 2/n², so repeat about n² log n times.

**Checking a matrix product (Freivalds).** To verify AB = C without multiplying, choose a random 0/1 vector r and test A(Br) = Cr in O(n²). A wrong C is caught with probability at least 1/2 per trial.

**Hashing.** A hash function chosen at random from a **universal family** gives expected O(1) operations whatever the keys. A fixed function always has bad inputs.

Randomness also gives simple algorithms where deterministic ones are complex: skip lists, treaps, reservoir sampling of a stream.

### Heuristics and local search
When no guarantee is available:

- **Local search:** start with any solution and repeatedly make an improving small change. It can get stuck in a **local optimum**.
- **Simulated annealing:** sometimes accept a worse solution, with a probability that falls over time, to escape local optima.
- **Genetic algorithms, tabu search** and others.

These often work very well and offer no proof. Measure them on realistic instances.

### Exact methods that are fast in practice
- **Branch and bound:** search the solution space, discarding branches that provably cannot beat the best found.
- **SAT and integer-programming solvers** routinely solve huge industrial instances.
- **Fixed-parameter algorithms:** exponential only in a small parameter k, such as O(2ᵏ·n).

### Online and streaming algorithms
- An **online** algorithm must decide without knowing future input. Its **competitive ratio** compares it with the best possible in hindsight. Cache-eviction policies are analysed this way.
- A **streaming** algorithm sees each item once and uses memory far smaller than the input.

> Key idea: Faced with a hard problem, decide what you can relax: optimality (approximate), certainty (randomise) or generality (special cases and parameters).
#Q What does a 2-approximation algorithm for a minimisation problem guarantee?

! The factor is proved for every input.
#Q Why does choosing a random pivot protect quicksort against worst-case inputs?

#LESSON String algorithms and algorithm engineering | 13
### Pattern matching
Find every occurrence of a pattern of length m in a text of length n. The naive method takes O(nm).

**Knuth-Morris-Pratt (KMP).** On a mismatch, do not start again. Use what was already matched. A **failure table**, computed from the pattern alone, gives for each position the length of the longest proper prefix of the pattern that is also a suffix of the part matched so far. The text pointer never moves backwards. Total time O(n + m).

**Rabin-Karp.** Compare **hashes** of the pattern and of each window of the text. A **rolling hash** updates the window's hash in O(1) as it slides: remove the leading character's contribution, add the new one. Expected O(n + m). It extends naturally to searching for many patterns and to detecting duplicated content.

**Boyer-Moore.** Compare from the end of the pattern and skip ahead by large steps. On typical text it examines only a fraction of the characters, and is what many tools use.

### Many patterns
- A **trie** stores a set of strings by shared prefixes.
- The **Aho-Corasick** automaton adds failure links to a trie and finds all occurrences of all patterns in one pass. It is used in intrusion detection and content filtering.

### Indexing a text
To search one large text many times, build an index.

- A **suffix array** lists all the suffixes in sorted order. A pattern is found by binary search in O(m log n).
- A **suffix tree** supports O(m) search and many other queries.
- The **Burrows-Wheeler transform** and the **FM-index** give a compressed index. They are the basis of the tools that align DNA sequencing reads to a genome.

### Compression
- **Huffman coding** gives frequent symbols shorter codes; it is the optimal prefix code for known symbol frequencies.
- **Lempel-Ziv** methods replace repeated substrings with references to earlier occurrences. Combined with Huffman coding they form the common general-purpose formats.

### Algorithm engineering
Theory ranks algorithms by asymptotic growth. Practice has to deal with real machines.

- **Constant factors.** Insertion sort beats merge sort for small n, so production sorts switch to it for small subarrays. The best algorithms are often **hybrids**.
- **The memory hierarchy.** An algorithm that touches memory sequentially can outrun one with a better Big O that jumps about.
- **Real data.** Timsort, used by Python and Java, exploits runs that are already sorted and is linear on nearly sorted input.
- **Galactic algorithms** have the best known asymptotic bounds and constants so large that they would win only on inputs bigger than the universe.

### Choosing in practice
1. Use the standard library. It is tuned and tested beyond anything you will write.
2. Establish what n actually is. For n = 50, anything works.
3. If performance matters, measure on realistic data.
4. Read the literature before inventing.

### Proving an algorithm correct
A complete argument has three parts:

- **Partial correctness:** if it terminates, the answer is right. Use loop invariants or induction.
- **Termination:** a measure that strictly decreases.
- **Complexity:** a bound on time and space.

### Lower bounds
Sometimes you can prove that no algorithm does better. Comparison sorting needs Ω(n log n). Searching a sorted array by comparisons needs Ω(log n). **Adversary arguments** imagine an opponent who answers each query so as to keep the algorithm uncertain as long as possible. A matching upper and lower bound means the problem is solved, in the asymptotic sense.

> In industry: The ability to recognise "this is a matching problem", "this is a shortest path on a product graph" or "this is NP-hard, so approximate" is worth more than memorising any single algorithm.

! The text pointer never moves backwards.
#Q Why might an algorithm with a worse Big O run faster in practice?
- Big O is wrong
* Smaller constant factors and better use of the cache can dominate at realistic input sizes
- Compilers ignore complexity
! Asymptotics describe growth, not the cost at a particular size.

@solution
class UnionFind {
  constructor(n) {
    this.parent = [];
    this.rank = [];
    for (let i = 0; i < n; i++) { this.parent.push(i); this.rank.push(0); }
    this.sets = n;
  }
  find(x) {
    let root = x;
    while (this.parent[root] !== root) { root = this.parent[root]; }
    while (this.parent[x] !== root) { const next = this.parent[x]; this.parent[x] = root; x = next; }
    return root;
  }
  union(a, b) {
    const ra = this.find(a), rb = this.find(b);
    if (ra === rb) return false;
    if (this.rank[ra] < this.rank[rb]) this.parent[ra] = rb;
    else if (this.rank[ra] > this.rank[rb]) this.parent[rb] = ra;
    else { this.parent[rb] = ra; this.rank[ra]++; }
    this.sets--;
    return true;
  }
  connected(a, b) {
    return this.find(a) === this.find(b);
  }
  count() {
    return this.sets;
  }
}

function kruskal(n, edges) {
  const sorted = edges.slice().sort((x, y) => x[2] - y[2]);
  const uf = new UnionFind(n);
  let total = 0;
  for (const [u, v, w] of sorted) {
    if (uf.union(u, v)) total += w;
  }
  return uf.count() === 1 ? total : null;
}

function lcs(a, b) {
  let prev = new Array(b.length + 1).fill(0);
  for (let i = 1; i <= a.length; i++) {
    const cur = [0];
    for (let j = 1; j <= b.length; j++) {
      if (a[i - 1] === b[j - 1]) cur.push(prev[j - 1] + 1);
      else cur.push(Math.max(prev[j], cur[j - 1]));
    }
    prev = cur;
  }
  return prev[b.length];
}

function coinChange(coins, amount) {
  const best = new Array(amount + 1).fill(Infinity);
  best[0] = 0;
  for (let a = 1; a <= amount; a++) {
    for (const c of coins) {
      if (c <= a && best[a - c] + 1 < best[a]) best[a] = best[a - c] + 1;
    }
  }
  return best[amount] === Infinity ? -1 : best[amount];
}

#LESSON Processor design: instructions and pipelines | 14
Software runs on hardware whose behaviour shapes performance in ways no algorithm analysis reveals. This course explains what the machine really does.

### The instruction set architecture
The **instruction set architecture** (ISA) is the contract between hardware and software: the instructions, the registers, and how memory is addressed. x86-64, ARM and RISC-V are the main ones.

- **RISC** designs have few, simple, fixed-length instructions: ARM, RISC-V.
- **CISC** designs have many, some complex, of variable length: x86.

Modern x86 processors translate their instructions internally into simple micro-operations, so the practical difference has narrowed.

### The basic cycle
A processor repeats: **fetch** an instruction, **decode** it, **execute** it, access **memory** if needed, and **write back** the result.

### Pipelining
Doing all five steps for one instruction before starting the next wastes hardware. A **pipeline** overlaps them, like an assembly line.

```diagram
   time -->     1     2     3     4     5     6     7
   instr 1     F     D     E     M     W
   instr 2           F     D     E     M     W
   instr 3                 F     D     E     M     W
```

Each instruction still takes five steps, but one **completes** every cycle. Throughput rises roughly by the number of stages.

### Hazards
Pipelining assumes instructions are independent. They are not.

- **Data hazards:** an instruction needs a result that an earlier one has not yet written. Remedies: **forwarding** the value directly between stages, or **stalling**.
- **Control hazards:** after a branch, which instruction comes next? The processor does not know until the branch is evaluated, several stages later.

### Branch prediction
Processors **guess** the outcome of each branch and carry on executing speculatively. If the guess was right, no time is lost. If wrong, the speculative work is discarded and the pipeline refilled: a penalty of 15 to 20 cycles on a modern processor.

Predictors learn from history and exceed 95% accuracy on typical code. Branches that follow no pattern, such as a comparison on random data, are mispredicted about half the time and can dominate the running time of a loop. This is why processing sorted data can be several times faster than processing the same data unsorted.

### Out-of-order and superscalar execution
Modern processors go far beyond a simple pipeline.

- **Superscalar:** several instructions are fetched and executed per cycle.
- **Out-of-order execution:** instructions run as soon as their inputs are ready, not in program order. Results are committed in order, so the program sees sequential behaviour.
- **Register renaming** removes false dependencies between instructions that merely reuse a register name.

A modern core holds hundreds of instructions in flight at once. What limits it is **dependency chains**: a long sequence in which each step needs the previous result cannot be parallelised, whereas independent operations overlap freely.

### Speculation and security
**Spectre** and **Meltdown** (2018) showed that speculative execution leaves traces in the cache that can be measured, leaking data across security boundaries. The processor discards wrong results but not their side effects on timing. Performance features had become security flaws, and the mitigations cost measurable speed.

### Power
For decades, transistors shrank and clock speeds rose. Around 2005 power density and heat ended the rise in clock frequency. Performance gains since then have come from more cores and from specialised hardware. Software has had to become parallel to keep getting faster.

> Key idea: A modern processor is a speculative, out-of-order, parallel machine pretending to execute one instruction at a time. Code that is predictable and has short dependency chains runs fastest.

#LESSON Caches and virtual memory | 14
### Cache organisation
A cache holds copies of recently used memory in **blocks** (cache lines), typically 64 bytes. Given an address, the cache must find the block quickly. The address is split:

```diagram
   | ------------- tag ------------- | --- index --- | -- offset -- |
        identifies which block           which set      byte within
        is stored there                                 the block
```

- **Direct-mapped:** each block can live in exactly one place. Fast, but two hot blocks that map to the same place evict each other continually (**conflict misses**).
- **Fully associative:** a block may go anywhere. Flexible, but every entry must be searched.
- **Set-associative:** the cache is divided into sets, each holding a few blocks (commonly 4 to 16 **ways**). The index selects the set; the tag is compared within it. This is the standard compromise.

### Three kinds of miss
- **Compulsory:** the first access to a block.
- **Capacity:** the working set is larger than the cache.
- **Conflict:** too many blocks map to the same set.

When a set is full, a block must be evicted, usually the **least recently used**.

### Writes
On a write, the cache line is updated and marked **dirty**; it is written to memory later. In a multi-core machine, each core has its own cache, and a **coherence protocol** (MESI) ensures that when one core writes a line, other cores' copies are invalidated. That traffic is the cost behind **false sharing**.

### Virtual memory
Each process sees its own large, private **virtual address space**. The hardware and operating system translate virtual addresses to **physical** ones.

Memory is divided into **pages**, typically 4 KB. A **page table** per process maps virtual pages to physical frames.

```diagram
   virtual address:   | virtual page number | offset |
                              |
                        [ page table ]
                              |
   physical address:  | physical frame number | offset |
```

What this provides:

- **Isolation:** a process cannot address another's memory.
- **More memory than exists:** pages not in use can be kept on disk.
- **Sharing:** one copy of a library is mapped into many processes.
- **Lazy allocation** and **copy-on-write**.

Page tables are themselves large, so they are organised as **multi-level** trees: four or five levels on 64-bit systems.

### The TLB
Walking the page table for every memory access would be far too slow. The **translation lookaside buffer** (TLB) caches recent translations. A TLB hit is nearly free; a miss costs a page-table walk of several memory accesses.

Programs that touch many pages scattered across memory suffer TLB misses. **Huge pages** (2 MB or 1 GB) let one TLB entry cover far more memory, which helps databases and other programs with large heaps.

### Page faults
Accessing a page that is not in physical memory causes a **page fault**. The operating system loads it, possibly from disk, evicting another page if memory is full. A fault that needs the disk costs millions of processor cycles.

**Thrashing:** when the active pages of running programs exceed physical memory, the system spends nearly all its time paging and almost none computing.

### Page replacement
Which page should be evicted?

- **Optimal:** the one not needed for the longest time. It requires knowing the future, so it serves only as a benchmark.
- **FIFO:** the oldest. Simple and often poor.
- **LRU:** the least recently used, which approximates the optimum using the past. Exact LRU is expensive, so systems use approximations such as the **clock** algorithm.

### Consequences for software
- Access memory sequentially where you can.
- Keep hot data compact and together.
- Be aware that a pointer dereference may cost a cache miss, a TLB miss, or both.
- Memory-mapped files let the operating system manage the paging of large data sets.

> Key idea: Every memory access passes through address translation and a hierarchy of caches. Locality makes both cheap; scattered access makes both expensive.

#LESSON Parallelism: laws and shared memory | 14
Since clock speeds stopped rising, more performance has meant more cores. Using them is harder than it looks.

### Amdahl's law
If a fraction **p** of a program can be parallelised and it runs on **n** processors, the speed-up is

```text
speed-up = 1 / ((1 − p) + p / n)
```

As n grows without limit, the speed-up approaches **1 / (1 − p)**.

| Parallel fraction | Maximum speed-up |
|---|---|
| 50% | 2× |
| 90% | 10× |
| 95% | 20× |
| 99% | 100× |

The **serial part dominates**. With 95% parallel code, a thousand cores give less than 20×. Removing serial bottlenecks is worth more than adding processors.

### Gustafson's law
Amdahl assumes a fixed problem size. In practice, with more processors we solve **bigger** problems, and the parallel part usually grows faster than the serial part. Measured this way, speed-up grows nearly linearly: **scaled speed-up = (1 − p) + p·n**. Both laws are correct; they answer different questions.

### What limits real speed-up
- The serial fraction.
- **Synchronisation:** contention for locks.
- **Communication** between threads or machines.
- **Memory bandwidth:** cores share the memory bus, so memory-bound code scales poorly.
- **False sharing** and cache-coherence traffic.
- **Load imbalance:** some workers finish early and wait.

Sometimes speed-up is **superlinear**: each worker's portion of the data now fits in cache.

### Shared-memory parallelism
Threads share an address space. This makes communication easy and safety hard.

Common patterns:

- **Parallel loops:** split independent iterations among threads.
- **Fork-join:** divide a problem recursively, solve the parts in parallel and combine. **Work stealing** balances the load: an idle thread takes tasks from a busy one.
- **Pipelines:** stages connected by queues.

Parallel loops are safe only if the iterations are independent. Summing into one shared variable is a data race; give each thread its own partial sum and combine at the end (a **reduction**).

### Memory models
Processors and compilers reorder operations. On most hardware, one thread's write may not be visible to another at once, and two threads may observe events in different orders.

A language's **memory model** defines what is guaranteed. The rule in nearly all of them: if two threads access the same variable, at least one writes, and there is no synchronisation, the behaviour is **undefined** or unpredictable. Use locks, atomics or message passing.

### Atomic operations and lock-free code
Processors provide **atomic** instructions. The most important is **compare-and-swap** (CAS): "if this location still holds the value I expect, replace it with a new value, as one indivisible step".

```text
loop:
    old = read(counter)
    if compare_and_swap(counter, old, old + 1): break
```

**Lock-free** data structures built on CAS guarantee that some thread always makes progress, and cannot deadlock. They are notoriously hard to get right. A classic trap is the **ABA problem**: a value changes from A to B and back to A, and a CAS wrongly concludes that nothing happened. Use library implementations.

### NUMA
In large servers, each processor socket has its own memory. Accessing another socket's memory is slower. **NUMA-aware** software keeps each thread's data on its own node.

### Parallel thinking
Not every problem parallelises. Some are **embarrassingly parallel** (rendering frames, processing independent requests). Some need clever decomposition. Some, with long chains of dependent steps, appear inherently sequential.

Design for parallelism from the start: minimise shared mutable state, prefer immutable data, and partition work so that workers rarely need to communicate.

> Key idea: Amdahl's law says the serial fraction sets the ceiling. Find it and shrink it before adding cores.

#LESSON Data parallelism: SIMD and GPUs | 13
Running several threads is one kind of parallelism. Another is applying the same operation to many pieces of data at once.

### Flynn's taxonomy
| Class | Meaning | Example |
|---|---|---|
| SISD | One instruction stream, one data stream | A classic single core |
| SIMD | One instruction, many data | Vector instructions, GPUs |
| MIMD | Many instructions, many data | Multicore, clusters |

### SIMD
**Single instruction, multiple data**: processors have wide registers (128, 256 or 512 bits) that hold several numbers, and instructions that operate on all of them at once.

```diagram
   scalar:   a0 + b0        one addition per instruction

   SIMD:    [a0 a1 a2 a3 a4 a5 a6 a7]
          + [b0 b1 b2 b3 b4 b5 b6 b7]      eight additions in one instruction
          = [c0 c1 c2 c3 c4 c5 c6 c7]
```

Compilers **auto-vectorise** simple loops. To help them:

- Use plain loops over contiguous arrays.
- Avoid dependencies between iterations (`a[i] = a[i − 1] + 1` cannot be vectorised directly).
- Avoid branches and function calls inside the loop.
- Assure the compiler that pointers do not alias.

Where that is not enough, libraries and **intrinsics** give direct access. SIMD is behind fast string search, JSON parsing, image and audio codecs, and numerical libraries.

### GPUs
A **graphics processing unit** has thousands of simple cores designed to perform the same computation on many data elements. Built for pixels and vertices, it turned out to suit any data-parallel workload, above all linear algebra.

| | CPU | GPU |
|---|---|---|
| Cores | A few to dozens, complex | Thousands, simple |
| Good at | Branching, sequential logic, low latency | Uniform arithmetic over huge arrays |
| Optimised for | Latency of one task | Total throughput |

A GPU program (a **kernel**) runs once per element, across thousands of threads. The model works when:

- the same operation applies to every element,
- elements are largely independent,
- there is enough data to justify the cost of transferring it to the device.

Code full of unpredictable branches or pointer chasing runs poorly on a GPU.

### Why deep learning uses GPUs
Training a neural network is, almost entirely, multiplying large matrices. That is uniform, independent arithmetic at enormous scale: exactly what GPUs do. The same model may train tens of times faster than on processors alone. Specialised accelerators push further by designing the hardware round that one workload.

### The memory bottleneck
A GPU has its own memory. Moving data between host memory and the device is slow relative to computing on it. Efficient programs keep data on the device and minimise transfers. For large models, memory capacity, not arithmetic speed, is often the limit.

### Heterogeneous computing
Modern systems combine processors, GPUs and specialised accelerators. The engineering problem is deciding which work goes where and moving data efficiently between them.

### Specialisation
With general-purpose processors no longer speeding up quickly, performance now comes from **specialised hardware**: GPUs, accelerators for neural networks, video codecs, cryptography and network processing. The trade is flexibility for efficiency, often a hundredfold in performance per watt.

### Practical guidance
- First make the algorithm and memory layout good.
- Use libraries that already exploit SIMD and GPUs.
- Arrange data as **structures of arrays** so that fields are contiguous.
- Measure. Data-parallel speed-ups are large when the workload fits and negative when it does not.

> Key idea: Data parallelism applies one operation to many values at once. It demands regular, independent, contiguous data, and rewards it with order-of-magnitude gains.

#LESSON Parallel programming models and correctness | 13
### Message passing
Instead of sharing memory, processes can each own their data and **communicate by sending messages**. There are no data races, since nothing is shared. The cost is copying and the need to design protocols.

- **MPI** is the standard in scientific computing: programs run as many processes across a cluster, exchanging messages explicitly.
- The **actor model** (Erlang, Akka): each actor has private state and a mailbox, and processes one message at a time.
- **Channels** (Go, Rust): typed conduits between concurrent tasks.

"Do not communicate by sharing memory; share memory by communicating."

### MapReduce and dataflow
For very large data sets across many machines, the **MapReduce** model asks the programmer for two functions:

- **map** turns each input record into key-value pairs;
- **reduce** combines all the values for each key.

```diagram
   input splits -->  map  -->  shuffle (group by key)  -->  reduce  -->  output
   "a b a"           (a,1)(b,1)(a,1)      a: [1,1,1]         a: 3
   "b a"             (b,1)(a,1)           b: [1,1]           b: 2
```

The framework handles distribution, scheduling and failure. This works because map and reduce are **pure functions**: a failed task can simply be run again.

Successors such as Spark generalise this to graphs of transformations on distributed collections, keep data in memory and optimise the whole plan. **Stream processing** applies the same ideas to unbounded data arriving continuously.

### Why functional ideas help
Parallelism is easy when there is no shared mutable state. Pure functions and immutable data can be run in any order, on any machine, any number of times. This is why functional style keeps appearing in parallel and distributed frameworks.

A reduction can be parallelised when its operation is **associative**: (a + b) + c = a + (b + c). The work can then be split into a tree. Floating-point addition is only approximately associative, so parallel sums may differ slightly from sequential ones.

### Task parallelism and futures
A **future** (or promise) represents a result that will be available later. Composing futures expresses concurrent computations without explicit threads. **Structured concurrency** ties the lifetime of concurrent tasks to a scope, so that none is leaked and errors propagate.

### Correctness
Concurrent programs fail in ways that sequential ones cannot.

- **Safety:** nothing bad happens (no data race, no violated invariant).
- **Liveness:** something good eventually happens (no deadlock, no starvation).

**Linearizability** is the standard correctness condition for concurrent objects: each operation appears to take effect at a single instant between its call and its return, consistent with a sequential history.

### Testing concurrent code
Bugs depend on timing and may appear once in a million runs.

- **Stress testing** with many threads and iterations.
- **Race detectors** (ThreadSanitizer) find data races by instrumenting memory accesses.
- **Deterministic simulation:** control the scheduler and the clock, so that any failing interleaving can be replayed exactly. Several databases are tested this way.
- **Model checking** systematically explores interleavings of a simplified model.
- **Property-based testing** generates random operation sequences and checks them against a sequential specification.

### Designing for correctness
- Minimise shared mutable state.
- Prefer immutable data and message passing.
- Encapsulate synchronisation inside well-tested abstractions.
- Use higher-level constructs (parallel loops, concurrent collections, actors) over raw threads and locks.
- Document which lock protects which data, and the order in which locks are taken.
- Use a language that checks it for you where you can. Rust rules out data races at compile time.

### The scale-up and scale-out choice
One large machine is simpler and avoids network failure modes. A cluster scales further and tolerates failure. Many workloads assumed to need a cluster fit comfortably on one modern server with hundreds of gigabytes of memory. Measure before distributing.

> Key idea: The easiest parallel programs to get right share nothing mutable. Push state to the edges and make the core a composition of pure transformations.

function amdahl(p, n) {
  return Math.round((1 / ((1 - p) + p / n)) * 100) / 100;
}

function gustafson(p, n) {
  return Math.round(((1 - p) + p * n) * 100) / 100;
}

function splitAddress(address, blockSize, numSets) {
  const offset = address % blockSize;
  const block = Math.floor(address / blockSize);
  return { tag: Math.floor(block / numSets), index: block % numSets, offset };
}

function fifoFaults(pages, frames) {
  const memory = [];
  let faults = 0;
  for (const page of pages) {
    if (memory.includes(page)) continue;
    faults++;
    if (memory.length >= frames) memory.shift();
    memory.push(page);
  }
  return faults;
}

function lruFaults(pages, frames) {
  const memory = [];
  let faults = 0;
  for (const page of pages) {
    const at = memory.indexOf(page);
    if (at !== -1) {
      memory.splice(at, 1);
      memory.push(page);
      continue;
    }
    faults++;
    if (memory.length >= frames) memory.shift();
    memory.push(page);
  }
  return faults;
}

function mapReduceCount(lines) {
  const pairs = [];
  for (const line of lines) {
    for (const word of line.split(" ")) {
      if (word !== "") pairs.push([word, 1]);
    }
  }
  const counts = {};
  for (const [word, one] of pairs) {
    counts[word] = (counts[word] || 0) + one;
  }
  return counts;
}

#W Explain how a processor translates a virtual address into a physical one, including the roles of the page table and the TLB, and describe what happens on a TLB miss and on a page fault. Explain why programs with good locality run faster.
+ Virtual address split into page number and offset; the page table maps page to frame
+ The TLB caches recent translations to avoid a page-table walk
+ TLB miss: the page table is walked, costing extra memory accesses
+ Page fault: the page is not in memory; the operating system loads it, possibly from disk, at very high cost
+ Good locality keeps accesses within pages and cache lines already loaded, so both the TLB and the caches hit
